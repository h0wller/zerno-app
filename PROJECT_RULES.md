# Архитектурный манифест и правила разработки: zerno-app

Документ содержит обязательные инженерные стандарты проекта `zerno-app` (Dual-Brand PWA / Telegram Mini App: «…и кофе» и «Пятница»).

**Любые изменения кодовой базы (человеком или AI-ассистентом) обязаны следовать этим правилам.** При конфликте этого манифеста с конкретной реализацией сначала проверьте код и ADR; не переносите старое правило без проверки.

---

## 1. Реактивность DOM и MutationObserver (ADR-008)

- Нельзя передавать `document.body` или `document.documentElement` в `.observe()`.
- Наблюдать разрешено только изолированные контейнеры компонентов.
- Количество observers ограничено и проверяется `scripts/audit-observers.mjs`; перед добавлением нового экземпляра проверьте реестр и архитектуру.
- Одноразовый observer отключается сразу после целевого события. Если состояние уже достигнуто, observer не создаётся.
- Предпочтение: прямой вызов функции или явное событие через `window.ztBus`; MutationObserver не является механизмом межмодульной коммуникации.

Полная мотивация и жизненный цикл описаны в `docs/architecture/adr-dom-reactivity.md`.

## 2. CSS: четыре логических слоя ответственности

Четыре слоя — это логические владельцы стилей. Брендовый слой имеет подслои 2a и 2b; они не являются дополнительными независимыми слоями. Логический порядок не следует автоматически трактовать как фактический порядок cascade.

1. **Слой 1 — `public/app/ui/theme/*.css`:** нейтральная база UI, общая геометрия и компонентные основы. Не добавлять новые брендовые значения или брендовые селекторы; использовать токены. Не добавлять `!important`, кроме уже документированных системных исключений.
2. **Слой 2a — `public/app/ui/brand-tokens.css`:** только CSS custom properties для брендов. Без раскладки и компонентных селекторов.
3. **Слой 2b — `public/app/core/views.js`:** динамические layout/media правила и брендовые поведенческие переопределения. Не переопределять сами значения токенов, принадлежащие слою 2a. Брендовые селекторы должны быть явными.
4. **Слой 3 — стили компонента рядом с владельцем поведения:** допускаются только стили, принадлежащие самому компоненту; цвета через токены, без дублирования глобальной геометрии.
5. **Слой 4 — минимальный critical CSS в `public/index.html`:** резервирует только первый кадр и предотвращает FOUC/CLS. Не превращать его во второго владельца компонента.

Это четыре верхнеуровневых слоя, где 2a/2b — две части слоя 2. Каноническое подробное описание, фактические исключения, загрузка файлов и cascade находятся в `docs/css-architecture.md`. Не использовать старые формулировки «Слой 0», «theme-v2.css» или правило «вся геометрия всегда только в theme»: они не описывают текущую структуру.

Автоматическая проверка: `scripts/css-audit.mjs`. Успех скрипта не заменяет review каскада и responsive-визуализации.

## 3. DOM ownership и события

- Один DOM-узел и одна изменяемая модель состояния имеют одного владельца. Другие модули используют документированные контракты и события.
- Межмодульные события проходят через `window.ztBus` (`public/app/core/bus.js`) или явный контракт, указанный в `docs/module-map.md`.
- Не добавлять monkey-patching глобальных функций ради связи модулей.
- `public/app/main.js` содержит статические импорты; `bus.js` импортируется первым, `boot.js` — последним. Актуальную карту импортов проверяйте в исходном файле.

Канонический ownership: `docs/module-map.md`. Обновляйте карту в том же PR, что и создание, перенос, переименование или удаление модуля либо перенос владения DOM.

## 4. Бренды и адаптивность

- Проверяйте затронутые пользовательские потоки минимум в `coffee` и `delivery`.
- Смена бренда не должна оставлять чужие тексты, логотипы, категории, цены, фавиконы или состояние корзины.
- На мобильных устройствах проверяйте safe-area, горизонтальный overflow, клавиатуру, фокус и реальные размеры hit-targets.
- В Telegram Mini App отдельно проверяйте MainButton, жесты закрытия и конфликт свайпов со шторками.

## 5. Производительность и изображения

- Не фиксируйте число eager-картинок «первые четыре» без проверки реальной первой строки. Приоритет должен соответствовать фактической геометрии LCP и первому ряду карточек.
- Для изображений и карточек резервируйте геометрию до загрузки медиа.
- Для медленной сети проверяйте first paint → hydrated page, поздние CSS и шрифты, CLS и горизонтальный overflow. Не ослабляйте assertions вместо исправления причины.
- Правила image compression и реальные критерии проверяйте по текущему `menu-editor.js` и тестам перед изменением документации.

## 6. Заказ и повторные запросы

- Клиентская блокировка кнопки предотвращает повторный клик в одной активной странице, но сама по себе не гарантирует серверную идемпотентность после таймаута, перезагрузки или повторной доставки запроса.
- Не заявлять, что дублирование заказов исключено, пока серверная гарантия и её интеграционные тесты не подтверждены. Для API-контракта сверяться с текущими роутами и `docs/openapi.yaml`.

## 7. Проверки и кэш

Скрипты проекта из `package.json` — источник истины. Основные команды:
- `npm run pretest` — статические guardrails и unit/integration suite.
- `npm run audit` — полный набор локальных проверок, включая линтеры, contract smoke и Playwright build/E2E.
- `npm run build:client` — bump service-worker/cache-busting версии и сборка клиентского bundle.
- `npx playwright test` — запуск браузерных сценариев.
- `npm run ui:baseline` — обновление baseline snapshots, а не обычная команда проверки; используйте только при намеренном утверждении нового эталона.

Не копируйте в документы числа passed/failed из старых запусков как актуальный статус. Для каждого PR указывайте commit SHA и конкретный CI run.

Изменения файлов `public/*` требуют соблюдения механизма cache-busting из `scripts/bump-sw.mjs`; не инкрементируйте версии вручную без проверки скрипта.

## 8. CI/CD и персонал

- CI workflow: `.github/workflows/ci.yml`; deploy workflow: `.github/workflows/deploy.yml`.
- Node version и реальные команды определяются `package.json` и CI workflow, не устаревшими текстовыми примерами.
- Секреты и production-коды берутся из окружения; не копировать значения секретов в документацию.
- Правила активации, деактивации ролей и диагностики сверять с серверными маршрутами перед изменением runbook.

## 9. Инструменты и процесс

- Новая возможность: spec → plan → implementation → tests → review.
- При использовании библиотеки/API — Context7, если актуальность интерфейса важна.
- Перед удалением кода/файлов проверьте связи через Graphify и реальные импорты.
- Ponytail: минимальный diff, сохранение поведения, не устранять «дубли» только ради нулевого числа, если различаются бизнес-контракты.
- EGM: фиксировать finding, evidence, disposition, residual risk и точный проверенный commit; не называть same-context review независимой проверкой.
- Перед PR: проверить полный diff, CI, smoke и визуальные сценарии. Не мерджить визуальный PR только по статическому зелёному CI.
- Любой факт, не проверенный по коду или CI текущей ветки, маркировать как предположение или historical note.
