# Архитектурный манифест и правила разработки: zerno-app

Документ содержит обязательные инженерные стандарты проекта `zerno-app` (Dual-Brand PWA / Telegram Mini App: «…и кофе» и «Пятница»).

**Любые изменения кодовой базы (человеком или AI-ассистентом) обязаны строго следовать этим правилам.**

---

## 1. Реактивность DOM и MutationObserver (ADR-008)

1. **Полный запрет на `document.body`:**

* Запрещено передавать `document.body`, `document.documentElement` или конструкции вида `(el || document.body)` в метод `.observe()`.
* Наблюдение разрешено только за изолированными листовыми контейнерами (например, конкретная модалка или панель).

1. **Строгая квота и реестр (White-list):**

* В проекте действует жесткий лимит на количество `MutationObserver` (валидируется скриптом `scripts/audit-observers.mjs`).
* Разрешенные точки:
* `public/app/cashier.js` (контейнер `cash-view`)
* `public/app/core/chat-head.js` (самоотключающийся наблюдатель шапки чата)
* `public/app/core/overlay-core.js` (изолированный `#cartPanel` в контексте Telegram)
* `public/app/core/swipe.js` (самоотключающийся хинт первого свайпа)
* `public/app/core/views.js` (центральный координатор шторки `#panel`)

* Добавление новых экземпляров без изменения архитектуры и согласования квоты запрещено.

1. **Принцип самоотключения (Self-Disconnecting):**

* Одноразовые наблюдатели обязаны вызывать `observer.disconnect()` сразу после наступления целевого состояния.
* Если состояние уже зафиксировано (например, флаг в `sessionStorage` или элемент уже в DOM), наблюдатель не должен создаваться вовсе.

## 2. CSS-архитектура: слои ответственности и загрузочный контур

CSS разделён на четыре логических слоя ответственности. Слой 2 содержит два разных механизма: токены-данные и runtime/layout-правила. Inline critical CSS и загрузочный fallback в `index.html` относятся к первому кадру и совместимости загрузки, а не являются альтернативным местом для обычных компонентных стилей. На базовом коммите `4bd2fd3` в `theme/` находится 31 CSS-файл; число файлов не является фиксированной частью архитектурного контракта.

Важно: четыре слоя описывают ответственность, а не гарантированный хронологический порядок применения CSS. Внешние stylesheet links, inline critical CSS и поздняя runtime-инъекция `views.js` взаимодействуют через обычный cascade; перемещение правил требует браузерной проверки.

Проверки `scripts/css-audit.mjs` подтверждают только перечисленные в самом скрипте ограничения. Они не являются полноценным CSS-парсером и не доказывают отсутствие всех конфликтов каскада или дублирующих правил.

### Слой 1 — `public/app/ui/theme/*.css` и `public/app/ui/fonts.css`

Базовые компоненты и нейтральная геометрия: reset, типографика, сетки, карточки, кнопки, модалки, панели, рейлы и responsive-правила.

Обязательные границы:
- Не добавлять `!important`, кроме системного правила для `[hidden]`.
- Не добавлять селекторы `[data-brand="..."]`: брендовые отличия принадлежат runtime-слою.
- Не хардкодить известные брендовые цвета Delivery в theme CSS; использовать семантические токены. Список проверяемых значений в `scripts/css-audit.mjs` ограничен и не является универсальным детектором брендовой палитры.
- Сохранять канонический порядок файлов и не создавать новые дублирующие патчи в конце каскада. Повтор селектора в разных media/state-контекстах может быть намеренной responsive-послойностью.

### Слой 2а — `public/app/ui/brand-tokens.css`

Только данные брендовой темы: custom properties на разрешённых селекторах `html[data-brand="..."]` и/или `body[data-brand="..."]`.

Не размещать здесь декларации обычных CSS-свойств, компонентные селекторы или layout-правила. Токены являются источником значений для брендовых runtime-переопределений.

### Слой 2б — `public/app/core/views.js`

Единственный централизованный runtime style block, создаваемый через `<style>` и массив `rules`. Он содержит:
- layout/system-правила, необходимые runtime-оболочке и адаптивному поведению;
- брендовые переопределения с `[data-brand=...]`, использующие семантические значения из `brand-tokens.css`;
- ограниченные правила совместимости/состояний, которые по текущей DOM-архитектуре принадлежат координатору видов.

Не предполагать, что каждый селектор в `views.js` обязан начинаться с `[data-brand]`: текущий `scripts/css-audit.mjs` явно допускает набор общих layout/system-селекторов и media/keyframes. Не определять здесь custom properties: их домен — `brand-tokens.css`. Лимит количества вхождений `[data-brand=` — 85, проверяется аудитом. Не добавлять новые inline-страховки `!important`.

`views.js` также владеет переключением видов и отдельными DOM-переездами; это отражено в `docs/module-map.md`. Наличие у модуля DOM/runtime обязанностей не означает, что любой связанный CSS автоматически должен попасть в его массив.

Перенос layout-правила из `views.js` в theme или обратно — архитектурное изменение: требуется сверить владельца, каскад, DOM-порядок и аудит, а не просто руководствоваться типом селектора.

### Слой 3 — компонентные модули

Локальные динамические стили и состояния, напрямую принадлежащие компоненту: например, локальная инъекция из `delivery.js`, общие динамические UI-правила из `ui/styles.js`, состояния и анимации чата. Эти стили не должны становиться вторым источником базовой геометрии или брендовой палитры.

- Использовать существующие CSS custom properties, не хардкодить брендовые значения.
- Не переписывать базовые/брендовые правила через компонентные monkey-patch-инъекции.
- При смене DOM ownership обновлять `docs/module-map.md` в том же PR.

### Слой 4 — `public/index.html`

Содержит два разных механизма, которые нельзя смешивать:

1. **Inline critical/first-frame CSS и ранние guards** — только правила, необходимые до загрузки внешних стилей для предотвращения FOUC и скачков геометрии первого кадра. Для зеркалируемых правил комментарий должен указывать соответствующий канонический источник; изменения обеих копий должны идти вместе.
2. **Загрузочный контур внешнего CSS** — обычные stylesheet links для fonts, theme и brand tokens, подключённые в числовом порядке, плюс эквивалентный набор в `<noscript>` как fallback. На базовом коммите stylesheet query versions синхронизированы с текущим `STATIC_CACHE`; конкретный номер версии не фиксируется в документации. Не менять этот механизм или порядок ради редизайна без отдельной проверки Safari/PWA/Telegram WebView.

### Проверка и кэширование

- `npm run pretest` запускает `scripts/css-audit.mjs`, `scripts/brands-check.mjs`, `scripts/audit-observers.mjs`, syntax checks и unit tests.
- `css-audit.mjs` читает все CSS-файлы `theme/` в естественном числовом порядке, извлекает массив `rules` из `views.js` и проверяет конкретные ограничения: `!important` в theme (с исключением `[hidden]`), отсутствие брендовых селекторов и известных цветов Delivery в theme, допустимый набор общих/брендовых селекторов в views, баланс скобок theme, известные разрывы слов, дубли селекторов в views, структурную корректность извлекаемого CSS, чистоту brand tokens, отсутствие token definitions в views и лимит брендовых правил. Проверка дубликатов theme работает как warning; responsive-послойность намеренно не считается ошибкой.
- Этот аудит не проверяет полностью CSS grammar, фактическую специфичность/порядок всех stylesheet-источников, все дубли между файлами и inline CSS, computed styles или визуальную идентичность первого кадра. Для этого нужны focused browser tests и визуальная проверка.
- Любые изменения внешних CSS-ассетов в `public/*` должны проходить существующий build/cache-busting механизм `npm run build:client` / `scripts/bump-sw.mjs`. Не менять `STATIC_CACHE` и версии ссылок вручную.

## 3. Межмодульная коммуникация: EventBus (`ztBus`)

1. **Запрет на Monkey-Patching:**

* Запрещено связывать логику через патчинг глобального объекта: `window.someFn = ...` с последующими проверками `if (typeof window.someFn === 'function')`.

1. **Событийная шина (`public/app/core/bus.js`):**

* Все межкомпонентные уведомления передаются через шину событий `window.ztBus`:

```javascript
// Отправка события
if (window.ztBus) window.ztBus.emit('ui:update-scrolltop');

// Подписка
if (window.ztBus) {
  window.ztBus.on('ui:update-scrolltop', update);
}

```

1. **Точка входа `public/app/main.js`:**

* Содержит **только статические импорты** модулей.
* Модуль `import './core/bus.js';` подключается первым.
* Модуль `import './core/boot.js';` подключается строго последним.
* Написание исполняемого кода, функций или логики внутри `main.js` запрещено.

## 4. Мультибрендовость и адаптивность

1. **Кросс-брендовая изоляция:**

* Любой компонент (меню, корзина, карточки, фильтры, касса) обязан тестироваться в двух режимах:
* `brand === 'coffee'` («…и кофе», кофейня)
* `brand === 'delivery'` («Пятница», доставка пиццы)

* Переключение брендов не должно оставлять артефактов в DOM (лишние кнопки, чужие категории, неверные фавиконы).

1. **Безопасные зоны мобильных устройств (Safe Area):**

* Плавающие элементы (`#scrollTopBtn`, `.chat-fab`, `#cartFab`, `#mbonusBtn`, модальные окна и шторки) обязаны учитывать safe-area:

```css
bottom: calc(20px + env(safe-area-inset-bottom, 0px));

```

1. **Telegram Mini App (TMA):**

* При открытии внутри Telegram нативная кнопка `Telegram.WebApp.MainButton` синхронизируется с состоянием корзины.
* Шторка заказов и попапы не должны конфликтовать со свайпом закрытия Telegram WebApp.

## 5. Производительность и оптимизация каталога (Lighthouse 90+)

1. **Загрузка и рендеринг изображений меню:**

* Первые 4 карточки витрины (Above-the-fold / LCP): `loading="eager"`, `fetchpriority="high"`.
* Карточки ниже первого экрана: `loading="lazy"`, `decoding="async"`, `content-visibility: auto`.
* Контейнеры изображений обязаны иметь явный `aspect-ratio` для устранения CLS (Cumulative Layout Shift).

1. **Клиентская компрессия при создании блюд (`menu-editor.js`):**

* Загрузка оригинальных фотографий размером > 1 МБ на сервер запрещена.
* Изображения сжимаются на клиенте через Canvas в формат WebP (макс. ширина 1000px, quality 0.82) перед отправкой в API.

1. **Идемпотентность оформления заказа:**

* Кнопка подтверждения заказа блокируется немедленно в момент первого клика с показом спиннера.
* Отправка заказа сопровождается клиентским идентификатором транзакции во избежание дублирования чеков при сетевых задержках.

## 6. CI/CD, Git Hooks и версионирование кэша

1. **Автоматический аудит:**

* Перед фиксацией изменений обязателен запуск:

```bash
npm run pretest

```

* Команда последовательно проверяет: синтаксис `views.js`, слои `css-audit.mjs`, манифест `brands-check.mjs` и лимиты `audit-observers.mjs`.

1. **Git Hook (`.githooks/pre-commit`):**

* Установлен в репозитории через `core.hooksPath = .githooks`.
* При каждом коммите автоматически инкрементирует `STATIC_CACHE` в `public/sw.js` через `scripts/bump-sw.mjs` и добавляет его в текущий индекс.
* Коммит отклоняется, если хотя бы один шаг аудита завершился с ошибкой.

1. **Коды сотрудников (F3.60):** источник правды — `.env` (`ADMIN_CODE/CASHIER_CODE/DISPATCH_CODE`), dev-дефолты в `server/config.js` не для прода. Смена кода = правка `.env` + `pm2 reload zerno-app`; активных сотрудников НЕ выкидывает (роль в `customers.role`, сессия — отдельная таблица `tokens`). Диагностика — `GET /api/tg/diag` → `codes_present`. Самопонижение админа кодом активации запрещено — `POST /api/auth/activate` вернёт 409 (снятие прав — только `/api/auth/deactivate`).

## 7. Инструкция для AI-ассистентов при генерации кода

При внесении любых правок в `zerno-app` искусственный интеллект обязан:

1. **Проверять влияние на оба бренда** (Coffee и Delivery).
2. **Не предлагать `MutationObserver**` — использовать прямое управление через `ztBus` или явные вызовы.
3. **Не использовать `!important**` в `theme/*.css`.
4. **Не добавлять код в `main.js**` кроме деклараций `import`.
5. **Предоставлять минимальный точечный дифф** без переписывания несвязанных функций.
Закон №1: Никакого rel="preload" onload="this.rel='stylesheet'" для базовых стилей.
fonts.css, части theme/*.css (по одному <link> на файл, в порядке номеров) и brand-tokens.css подключаются честным <link rel="stylesheet" href="/app/ui/theme/NN-name.css?v=XXX">. Это 35 КБ в gzip — они скачиваются за 40 мс, зато гарантируют 100% загрузку стилей в iOS Safari, PWA и Telegram WebView и навсегда убивают и FOUC, и CLS 1.365, и «голый HTML» на скринах!   Закон №2: Автоматический Cache-Busting (?v=XXX) в index.html через scripts/bump-sw.mjs.При каждом вызове npm run build:client скрипт bump-sw.mjs обновляет номер версии не только в public/sw.js (zerno-static-v440), но и автоматически проставляет ?v=440 в public/index.html для theme/*.css?v=440, brand-tokens.css?v=440 и /dist/main.bundle.js?v=440.Так query-version stylesheet/bundle и STATIC_CACHE обновляются одним механизмом; это снижает риск старых ассетов, но не является доказательством невозможности устаревшего кэша во всех браузерах и сетевых сценариях.Закон №3: `views.js` может содержать перечисленные в `scripts/css-audit.mjs` layout/system-селекторы, media/keyframes и брендовые overrides. Не расширять allowlist без обоснования. Правило о конкретном владельце геометрии определяется архитектурным контрактом и `docs/css-architecture.md`; не переносить CSS только по названию селектора.

Закон №4: Один канонический блок правила в рамках одного владельца/контекста. Не добавлять патчи в конец файла с повышенной специфичностью вместо изменения канонического правила. Повторения в разных media/state-контекстах могут быть необходимой responsive-послойностью; перед удалением проверять computed styles и каскад.Закон №5: Нативная шапка Telegram (body.in-tg).
Мы не добавляем искусственный padding-top: 56px к .topbar в body.in-tg, потому что WebView Telegram уже начинается под нативной шапкой мессенджера.

## Инструменты
- Новые фичи: spec → plan → build с тестами.
- Любая библиотека: сначала Context7, не API по памяти.
- Перед PR: ponytail-review, потом code-review-and-quality.
- Удаление кода или файлов: сначала Graphify, нет ли ссылок.
- Стэк-PR: CI не запускается, поэтому тесты, сборку и css-audit гоняй локально.
