# Архитектура, стек и инфраструктурный контекст проекта Zerno App

Этот документ предназначен для разработчиков и ИИ-ассистентов. Он описывает устройство системы, используемый стек, сетевые ограничения и правила кодовой базы, чтобы исключить галлюцинации и шаблонные рекомендации.

---

## 1. О проекте и бизнес-контексте

* **Суть проекта:** Мультибрендовое Progressive Web App (PWA) для двух заведений общественного питания в пгт. Янтарный (Калининградская область):

1. **«…и кофе»** — кофейня на побережье (система лояльности «каждый 10-й кофе в подарок», электронные штампы, меню напитков).

2. **«Пятница»** — доставка пиццы и роллов (каталог блюд, корзина с умными модификаторами и топпингами, валидация адресов по локальному справочнику, предзаказы).

* **Пользователи системы:**
* **Гости:** заходят через мобильные браузеры (преимущественно Safari на iOS и Chrome на Android) или Telegram Mini App.

* **Персонал:** кассиры (начисление штампов, списание бонусов через сканирование QR) и диспетчеры (управление статусами заказов доставки).

* **Администраторы:** управление меню, стоп-листами, промокодами и аналитикой.

## 2. Стек технологий и архитектура

### Бэкенд

* **Среда выполнения:** Node.js 22 (ESM).

* **Фреймворк:** Express 5.x (`express: ^5.3.0`) + `compression` (Gzip/Deflate).

* **База данных:** SQLite через драйвер `better-sqlite3` (локальная база с миграциями, WAL-режим).

* **Медиа-обработка:** `sharp` (автоматическая нарезка загруженных блюд в Retina WebP).

* **Уведомления:** Web Push (`web-push` через VAPID), Firebase Admin (`firebase-admin` для нативных пушей Capacitor), бот Telegram через вебхуки. Сервер использует встроенный глобальный `fetch` Node.js 22; `node-fetch` не является зависимостью проекта.

* **КРИТИЧЕСКИЙ ФАКТ:** В проекте **НЕТ WebSockets**! Все обновления заказов, журналов и чата работают через HTTP REST API с контролируемым поллингом (`/api/orders`, `/api/chat/thread`).

### Фронтенд

* **Архитектура:** Vanilla JavaScript (ESM-модули), объединённые сборщиком:

```bash
npm run build:client
# esbuild public/app/main.js --bundle --minify --sourcemap --format=esm --target=es2022 --outfile=public/dist/main.bundle.js

```

* **Точка входа:** `public/app/main.js`. Последним строго импортируется `boot.js`.

* **PWA & Offline:** Единый Service Worker (`public/sw.js`):

* `STATIC_CACHE` — App Shell (Cache-First с фоновой ревалидацией `cache: 'reload'`).

* `MEDIA_CACHE` — SVG (Network-First), растровые изображения (SWR).

* `API_CACHE` — кэширование меню (`/api/menu`, `/api/dmenu`) на 5 минут.

* **Стили (4-слойная архитектура):**

1. *Слой 1:* `public/app/ui/theme/*.css` (базовые токены и компоненты).

2. *Слой 2:* `public/app/ui/brand-tokens.css` (токены брендов) + `public/app/core/views.js` (layout и селекторы `[data-brand="delivery"]`).

3. *Слой 3:* Локальные инжекции CSS в компонентных модулях.

4. *Слой 4:* `public/index.html` (только критический Above-the-fold каркас).

## 4. Сетевая специфика РФ и инциденты (Памятка для ИИ)

При решении сетевых и инфраструктурных проблем **запрещено** применять шаблонные решения:

1. **Запрещено советовать VPN-протоколы (VLESS, REALITY, Hysteria2):** Клиенты сайта — обычные посетители кафе с iPhone, открывающие сайт в Safari. Браузер не может подключаться через кастомные туннели.
2. **Запрещено включать Cloudflare Proxy (оранжевое облако):** Публичные Anycast-пулы Cloudflare (`172.67.x.x`, `104.21.x.x`) в РФ глушатся сотовыми операторами (МТС, Мегафон) через принудительный TCP RST (`ERR_CONNECTION_RESET`). Для работы в РФ в Cloudflare используется **строго DNS Only (серое облако)**.
3. **Запрещено включать HTTP 103 Early Hints:** На мобильном Safari при работе через Service Worker ответы 103 ломают конвейер сетевых запросов движка WebKit, вызывая ошибку `NSURLErrorCancelled (-999)`.
4. **Природа блокировок хостинга:** Если запросы к серверу на 80/443 порты сбрасываются с ошибкой `Connection was reset`, значит, конкретная европейская подсеть дата-центра (`129.101.120.x`) попала под сигнатурные фильтры ТСПУ. Решается заменой публичного IPv4 на сервере или размещением Ingress-точки в РФ.
5. **Gcore CDN:** Использование Gcore в РФ сопряжено с риском нестабильности московских нод (`92.223.84.84`), которые также могут периодически фильтроваться магистральными провайдерами.

## 5. Правила разработки и Guardrails кодовой базы

Перед предложением любых изменений в коде необходимо соблюдать следующие правила:

* **Инкремент кэша Service Worker:** `npm run build:client` запускает `npm run bump:sw` (`scripts/bump-sw.mjs`) перед сборкой bundle. Поэтому ручной инкремент `STATIC_CACHE` не требуется, если перед релизом/проверкой выполняется штатная сборка. Не пропускайте сборку после клиентских изменений; поведение самого `public/sw.js` проверяйте по его текущему коду.

* **Правило одного владельца DOM (Single Source of Truth):** Никаких параллельных мутаций одного DOM-узла из разных модулей. Карта закреплена в `docs/module-map.md`:

* Корзина (`cart.js`) — единственный модуль, меняющий состояние корзины.

* Шапка и марка (`admin-extra.js` + `views.js`).

* Навигационный рейл (`menu.js` и `delivery.js`).

* **Безопасность Node.js:** Процесс Node 22 защищён глобальным перехватом `process.on('unhandledRejection')` от крэша при сетевых сбоях фоновых пушей. Не удалять этот обработчик в `server.js`.

* **Строгие проверки качества перед коммитом:**

```bash
npm run audit

```

Команда выполняет последовательность из скрипта `audit` в `package.json`:

1. `npm run check` → `node --check server.js`.
2. `npm run pretest` → синтаксическая проверка `views.js`, проверка существующего client bundle, CSS audit, brands-check, audit-observers и unit-тесты (`tests/unit` + `tests/integration`).
3. `npm run lint:code` → ESLint для `public/`, `server/`, `scripts/` с `--max-warnings 50` (ESLint 10 Flat Config + SonarJS).
4. `npm run lint:dup` → jscpd light и strict.
5. `npm run lint:dead` → Knip.
6. `npm run lint:layers` → dependency-cruiser.
7. `npm run smoke` → контрактные smoke-тесты.
8. `npm run test:e2e` → повторная сборка клиента и Playwright E2E.

Точные команды и состав шагов всегда сверяйте с корневым `package.json`: эта документация — пояснение, а не независимый источник конфигурации.

## SMS OTP (будущая платная функция)

- SMS.ru adapter `server/services/sms.js` остаётся в коде как интеграция, готовая к будущему запуску, но авторизация по SMS выключена по умолчанию.
- Пока функция не одобрена, `SMS_AUTH_ENABLED` должен отсутствовать или быть `false`. В этом состоянии адаптер прекращает работу до сетевого запроса, SMS UI скрыт, регистрации/вход не делают автоматический SMS fallback.
- Только после отдельного бизнес-одобрения можно задать `SMS_AUTH_ENABLED=true` вместе с `SMSRU_API_ID` в `/var/www/app/.env` и перезапустить `zerno-app`. Публичный `/api/config` раскрывает только `smsAuthEnabled`, не API-ключ.
- Не включать платный флаг в production/CI по умолчанию и не тестировать отправку на реальных номерах. Интеграционные тесты используют тестовый режим SMS-адаптера.

## 6. Коды сотрудников (F3.60)

* **Production secrets:** production-окружение должно явно задавать уникальные `ADMIN_CODE`, `CASHIER_CODE`, `DISPATCH_CODE`. Каждый код — не короче 16 и не длиннее 64 символов; допустимы латинские буквы, цифры, `_` и `-`. Runtime больше не подставляет встроенные значения. Пустой, отсутствующий или слишком короткий секрет не даёт активировать роль. Не хранить реальные значения в репозитории, документации или CI-конфигурации.
* **CI/test:** Playwright использует отдельные тестовые passphrase из test harness. Короткие legacy-значения, ещё передаваемые CI workflow в `ADMIN_CODE`/`CASHIER_CODE`/`DISPATCH_CODE`, короче нового минимума и намеренно игнорируются актуальным `playwright.config.js`; сервер их не принимает. Это временные тестовые значения, не production-секреты.
* **Генерация:** используйте [Bitwarden Password Generator](https://bitwarden.com/password-generator/): тип Password, длина 32, включить `A–Z`, `a–z`, `0–9`, отключить спецсимволы. Получить три независимых значения, каждое уникальное; допустимые символы совпадают с серверной валидацией. Генератор заявляет локальную генерацию на устройстве. Сохранить секреты в менеджере паролей и ввести сразу в production `.env`; не пересылать их в чаты, issues или git.
* **Смена кода:** обновить соответствующую переменную в `/var/www/app/.env` и выполнить `pm2 reload zerno-app`. Уже выданные роли и активные токены сохраняются: код проверяется только при `POST /api/auth/activate`; роль хранится в `customers.role`, сессия — отдельно в таблице `tokens`. Значения длиной меньше 16 символов после этого изменения больше не работают для новой активации.
* **Диагностика:** `GET /api/tg/diag` (adminGuard, обработчик в `server.js`) возвращает `codes_present: { admin, cashier, dispatch }`. Значение `true` означает, что соответствующий код задан и проходит минимальную проверку длины; сами коды наружу не выдаются.
* **Защита от самопонижения:** администратор не может понизить себя до кассира/диспетчера через `POST /api/auth/activate` (ответ `409`). Снятие прав — только через `POST /api/auth/deactivate` с защитой последнего администратора.

## 7. Регламент деплоя

Деплой на сервер автоматизирован через GitHub Actions (`.github/workflows/deploy.yml`):

* **Ветка для релиза:** `pizza`.

* **Триггер:** текущий `.github/workflows/deploy.yml` запускается **только вручную** через `workflow_dispatch`; push/merge в `pizza` и завершение `CI Quality Gates` сами по себе деплой не запускают. Для запуска требуется явно передать `confirm_production: true`; без этого job пропускается.
* **Пайплайн:** после подтверждённого ручного запуска на VPS выполняются `git fetch origin`, `git reset --hard origin/pizza`, `npm install --package-lock-only --ignore-scripts --no-audit --no-fund`, `npm ci`, `BUILD_NUM=$(git rev-list --count HEAD) npm run build:client`, `npm prune --omit=dev`, `pm2 reload zerno-app` и проверка `pm2 status zerno-app`.

* **Сборка клиента:** `build:client` запускается на сервере в deploy workflow и локально/в CI по необходимости. Скрипт сначала выполняет `bump:sw`, затем собирает `public/dist/main.bundle.js`. Локальная сборка перед каждым коммитом не является обязательным шагом deploy workflow.
