# Архитектура, стек и инфраструктурный контекст проекта Zerno App

Этот документ предназначен для разработчиков и ИИ-ассистентов. Он описывает устройство системы, используемый стек, сетевые ограничения и правила кодовой базы, чтобы исключить галлюцинации и шаблонные рекомендации.

---

## 1. О проекте и бизнес-контексте

* **Суть проекта:** Мультибрендовое Progressive Web App (PWA) для двух заведений общественного питания в пгт. Янтарный (Калининградская область):

1. **«…и кофе»** — кофейня на побережье (система лояльности «каждый 10-й кофе в подарок», электронные штампы, меню напитков).

2. **«Пятница»** — доставка пиццы и роллов (каталог блюд, корзина с умными модификаторами и топпингами, валидация адресов по локальному справочнику, предзаказы).

* **Пользователи системы:**
* **Гости:** заходят через мобильные браузеры (преимущественно Safari на iOS и Chrome на Android) или Telegram Mini App.

* **Персонал:** кассиры (начисление штампов, списание бонусов через сканирование QR) и диспетчеры (управление статусами заказов доставки).

* **Администраторы:** управление меню, стоп-листами, промокодами и аналитикой.

## 2. Стек технологий и архитектура

### Бэкенд

* **Среда выполнения:** Node.js 22 (ESM).

* **Фреймворк:** Express 4.x + `compression` (Gzip/Deflate).

* **База данных:** SQLite через драйвер `better-sqlite3` (локальная база с миграциями, WAL-режим).

* **Медиа-обработка:** `sharp` (автоматическая нарезка загруженных блюд в Retina WebP).

* **Уведомления:** Web Push (`web-push` через VAPID), Firebase Admin (`firebase-admin` для нативных пушей Capacitor), бот Telegram через вебхуки (`node-fetch` к `api.telegram.org`).

* **КРИТИЧЕСКИЙ ФАКТ:** В проекте **НЕТ WebSockets**! Все обновления заказов, журналов и чата работают через HTTP REST API с контролируемым поллингом (`/api/orders`, `/api/chat/thread`).

### Фронтенд

* **Архитектура:** Vanilla JavaScript (ESM-модули), объединённые сборщиком:

```bash
npm run build:client
# esbuild public/app/main.js --bundle --minify --sourcemap --format=esm --target=es2022 --outfile=public/dist/main.bundle.js

```

* **Точка входа:** `public/app/main.js`. Последним строго импортируется `boot.js`.

* **PWA & Offline:** Единый Service Worker (`public/sw.js`):

* `STATIC_CACHE` — App Shell (Cache-First с фоновой ревалидацией `cache: 'reload'`).

* `MEDIA_CACHE` — SVG (Network-First), растровые изображения (SWR).

* `API_CACHE` — кэширование меню (`/api/menu`, `/api/dmenu`) на 5 минут.

* **Стили (4-слойная архитектура):**

1. *Слой 1:* `public/app/ui/theme-v2.css` (базовые токены и компоненты).

2. *Слой 2:* `public/app/ui/brand-tokens.css` (токены брендов) + `public/app/core/views.js` (layout и селекторы `[data-brand="delivery"]`).

3. *Слой 3:* Локальные инжекции CSS в компонентных модулях.

4. *Слой 4:* `public/index.html` (только критический Above-the-fold каркас).

## 4. Сетевая специфика РФ и инциденты (Памятка для ИИ)

При решении сетевых и инфраструктурных проблем **запрещено** применять шаблонные решения:

1. **Запрещено советовать VPN-протоколы (VLESS, REALITY, Hysteria2):** Клиенты сайта — обычные посетители кафе с iPhone, открывающие сайт в Safari. Браузер не может подключаться через кастомные туннели.
2. **Запрещено включать Cloudflare Proxy (оранжевое облако):** Публичные Anycast-пулы Cloudflare (`172.67.x.x`, `104.21.x.x`) в РФ глушатся сотовыми операторами (МТС, Мегафон) через принудительный TCP RST (`ERR_CONNECTION_RESET`). Для работы в РФ в Cloudflare используется **строго DNS Only (серое облако)**.
3. **Запрещено включать HTTP 103 Early Hints:** На мобильном Safari при работе через Service Worker ответы 103 ломают конвейер сетевых запросов движка WebKit, вызывая ошибку `NSURLErrorCancelled (-999)`.
4. **Природа блокировок хостинга:** Если запросы к серверу на 80/443 порты сбрасываются с ошибкой `Connection was reset`, значит, конкретная европейская подсеть дата-центра (`129.101.120.x`) попала под сигнатурные фильтры ТСПУ. Решается заменой публичного IPv4 на сервере или размещением Ingress-точки в РФ.
5. **Gcore CDN:** Использование Gcore в РФ сопряжено с риском нестабильности московских нод (`92.223.84.84`), которые также могут периодически фильтроваться магистральными провайдерами.

## 5. Правила разработки и Guardrails кодовой базы

Перед предложением любых изменений в коде необходимо соблюдать следующие правила:

* **Инкремент кэша Service Worker:** Любая правка файлов в `public/*` **обязательно** сопровождается инкрементом версии `STATIC_CACHE` в `public/sw.js` (например, `zerno-static-v347 -> v348`), иначе мобильные клиенты PWA продолжат исполнять старый кэш.

* **Правило одного владельца DOM (Single Source of Truth):** Никаких параллельных мутаций одного DOM-узла из разных модулей. Карта закреплена в `docs/module-map.md`:

* Корзина (`cart.js`) — единственный модуль, меняющий состояние корзины.

* Шапка и марка (`admin-extra.js` + `views.js`).

* Навигационный рейл (`menu.js` и `delivery.js`).

* **Безопасность Node.js:** Процесс Node 22 защищён глобальным перехватом `process.on('unhandledRejection')` от крэша при сетевых сбоях фоновых пушей. Не удалять этот обработчик в `server.js`.

* **Строгие проверки качества перед коммитом:**

```bash
npm run audit

```

Команда запускает:

1. `node --check server.js`

2. `node scripts/css-audit.mjs` (проверка соблюдения 4 слоев CSS)

3. `eslint public/ server/ scripts/` (ESLint 9 Flat Config + SonarJS)

4. `jscpd` (проверка отсутствия дублирования логики и стилей)

5. `knip` (поиск неиспользуемого кода)

6. `dependency-cruiser` (контроль однонаправленности слоев: `server` не импортирует `public`, UI не зависит от деталей ядра).

## 6. Регламент деплоя

Деплой на сервер автоматизирован через GitHub Actions (`.github/workflows/deploy.yml`):

* **Ветка для релиза:** `pizza`.

* **Пайплайн:** Прохождение `CI Quality Gates` -> SSH-подключение к VPS Timeweb -> `git reset --hard` -> `npm ci --omit=dev` -> `pm2 reload zerno-app`.

* **Сборка клиента:** При изменениях в клиентском коде перед коммитом локально выполняется `npm run build:client`, формирующий `public/dist/main.bundle.js`.
