# Ролевое тестирование и список найденных исправлений

**Статус:** экспериментальная тестовая ветка `feat/test-role-switcher`.
**Важно:** не сливать эту ветку в `main`/`pizza` и не развёртывать на production без отдельного явного решения. Переключатель нужен для локального тестирования настоящих серверных ролей. Сохранять ветку как тестовый инструмент.

## Зачем нужна ветка

Проверять приложение под отдельными тестовыми профилями с реальными серверными правами, не меняя роль или сессию основного администратора. Роли переключения: гость, кассир, диспетчер.

Тестовые профили используют настоящие API и серверную авторизацию, а не визуальную имитацию. Поэтому созданные ими заказы и другие операции могут попадать в рабочие списки и менять данные подключённой базы. Для проверки предпочтительна локальная база с тестовыми данными.

## Найденные проблемы и задачи

### 1. Ограничить остановку позиций по бренду и роли

- **Кассир:** не должен иметь возможность ставить на стоп позиции меню доставки «Пятница» (включая вызовы API напрямую).
- **Диспетчер:** не должен иметь возможность ставить на стоп напитки кофейни «…и кофе» (включая вызовы API напрямую).
- Проверить не только видимость элементов интерфейса, но и серверную авторизацию/валидацию. Нельзя полагаться исключительно на скрытие кнопок.
- Добавить регрессионные проверки для разрешённых и запрещённых комбинаций роли и типа позиции.

### 2. Сверить часы работы доставки с `public/poster.html`

- Обновить расписание доставки в приложении в соответствии с информацией в `public/poster.html`.
- Перед реализацией прочитать источник и перенести фактические часы без догадок.
- Проверить все места, где расписание отображается или влияет на доступность заказа, чтобы не осталось разных значений.

### 3. Снизить заметность входа по коду сотрудника

- Убрать с гостевого экрана заметную кнопку **«У меня есть код доступа сотрудника»**.
- Перенести вход в менее заметное, но доступное сотрудникам место (вариант реализации выбрать при работе над UI).
- Полностью убрать текст **«Вкладки „Кассир“ и „Админ“ открываются только сотрудникам.»**
- Не раскрывать гостям лишние сведения о внутренних вкладках и способе активации ролей.
- Это изменение интерфейса не заменяет серверную защиту: все привилегированные операции должны оставаться защищены на backend.

## Порядок работы

1. Оставить `feat/test-role-switcher` отдельной тестовой веткой; не включать её в production-релиз.
2. Использовать тестовые профили для воспроизведения и проверки проблем.
3. Исправления бизнес-логики и UI переносить отдельными целевыми изменениями после проверки; не переносить автоматически сам переключатель ролей.
4. Для ограничений ролей проверить как интерфейс, так и прямые API-запросы.
5. Для часов доставки использовать `public/poster.html` как источник истины.

## Чек-лист регрессии

- [ ] Кассир не может остановить позицию доставки ни через UI, ни прямым запросом к API.
- [ ] Диспетчер не может остановить напиток кофейни ни через UI, ни прямым запросом к API.
- [ ] Разрешённые действия каждой роли по-прежнему работают.
- [ ] Часы доставки во всех нужных местах соответствуют `public/poster.html`.
- [ ] Гость не видит заметную кнопку входа по коду сотрудника.
- [ ] Указанный текст про вкладки «Кассир» и «Админ» удалён.
- [ ] Серверная авторизация не зависит от скрытия элементов интерфейса.
- [ ] Основной аккаунт администратора и его роль не изменены.
