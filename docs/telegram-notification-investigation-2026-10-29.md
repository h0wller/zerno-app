# Аудит Telegram-уведомлений и приветственных бонусов (2026-10-29)

## Краткий итог

Расследование выявило две связанные, но разные проблемы:

1. **Отправка Telegram:** `sendTg()` принимает ID клиента из `customers.id`, а не Telegram chat ID из `customers.tg`. При передаче chat ID функция искала клиента с таким первичным ключом и возвращала `{ ok: false, reason: 'no_tg' }`.
2. **Ложный успешный результат:** в production-ветке `pizza` на момент проверки `sendTg()` ожидала `tgSend()`, но не проверяла возвращённый результат. При отказе Telegram API функция могла записать `[push] tg ok` и вернуть `{ ok: true }`. Это не доказывало успешную отправку.

Отдельно найден путь, на котором приветственный бонус мог не начисляться: обработчик кассира верифицировал гостя, но не вызывал `grantBonus()`; кроме того, прежний backfill отмечал бонусы выданными всем клиентам, в том числе неподтверждённым профилям. Исправления кода подготовлены в [PR #63](https://github.com/h0wller/zerno-app/pull/63). На момент написания PR открыт и не считается задеплоенным.

## Что проверено в существующей документации

- `docs/api.md` перечисляет клиентский endpoint `POST /api/push/subscribe`, но не описывает контракт серверного `sendTg()`, обработку ошибок Telegram API или интерпретацию результата.
- `docs/module-map.md` указывает на фронтенд-модули уведомлений и общую серверную оркестрацию TG + Web Push + FCM, но не содержит runbook диагностики отправки.
- `tests/unit/telegram-link.test.mjs` проверяет привязку Telegram ID к профилю, повторную привязку и дубликаты. Это не тест отправки сообщения через Bot API.
- Найденный postmortem `docs/postmortem-2026-10-09-db-migration.md` относится к выбору файла SQLite при миграции меню и не описывает Telegram-уведомления.

Вывод: архитектурные упоминания уже были, но пошаговой документации расследования и чёткой границы между ID клиента, Telegram ID, принятием API и фактическим прочтением не было.

## Доказательства и наблюдения

### 1. Два разных идентификатора

В `server/services/push.js` функция `sendTg(cid, ...)` ищет профиль запросом по `customers.id`, затем берёт `customers.tg` как chat ID для `tgSend()`.

- `cid` / `customers.id` — внутренний ID клиента.
- `customers.tg` — Telegram chat ID.
- `tgSend(chatId, ...)` принимает уже Telegram chat ID.

Наблюдавшийся результат при передаче Telegram ID вместо внутреннего ID:

```text
[push] tg skip: cid=<telegram-chat-id> (нет привязанного Telegram)
RESULT: { ok: false, reason: 'no_tg' }
```

Безопасный порядок диагностики — сначала найти единственную запись клиента по `customers.tg`, проверить её `id`, затем передавать в `sendTg()` именно внутренний ID. При нуле или нескольких совпадениях отправку следует прервать, а не угадывать профиль.

### 2. Что доказывает лог отправки

В production-коде на ветке `pizza` вызов `tgSend()` не проверял его возвращаемое значение перед логом успеха. Поэтому `[push] tg ok` и `{ ok: true }` в этой версии не были надёжным подтверждением даже принятия сообщения Telegram API.

В коде PR #63 `tgSend()` возвращает структурированный результат:
- `{ ok: true, messageId }` при успешном ответе Bot API;
- `{ ok: false, reason: 'no_token' }` при отсутствии токена;
- `{ ok: false, reason: 'telegram_api_error', ... }` при ошибке API;
- `{ ok: false, reason: 'network_error', ... }` при сетевой ошибке.

`sendTg()` в PR #63 передаёт этот результат наверх и не объявляет ошибочный результат успешным.

Даже реальный успешный ответ `sendMessage` означает, что Telegram Bot API принял сообщение и вернул объект отправленного сообщения. Он **не подтверждает**, что пользователь открыл чат, получил уведомление на устройстве или прочитал текст. Для этого бот не предоставляет receipt о прочтении.

### 3. Проверка вручную

Во время расследования тест на собственный профиль с корректным внутренним ID клиента сработал. Затем команда для профиля Анны вернула лог `[push] tg ok` и `{ ok: true }`. В логах были реальные идентификаторы получателей; они намеренно не сохраняются в этой документации.

Важно: второй результат был получен на production-версии до подтверждённого деплоя изменений PR #63. Поэтому один только этот лог нельзя считать независимым доказательством принятия сообщения Telegram API. Факт получения сообщения у адресата подтверждается только проверкой чата адресата; для будущих отправок следует использовать версию с корректной передачей результата API.

### 4. Начисление приветственных бонусов

В ходе смежного аудита бонусов обнаружено:

- прежний backfill в `server/db/schema.js` отмечал `signup`, `qr` и `install` как выданные для каждого клиента. Это могло блокировать приветственный бонус у неподтверждённого гостя;
- кассовый путь `POST /api/staff/customers` мог верифицировать существующего гостя или создать нового подтверждённого гостя без вызова `grantBonus()`;
- изменение миграции само по себе не восстанавливает состояние production-строк, которые уже были отмечены предыдущим backfill.

PR #63 меняет backfill, добавляет вызов `grantBonus()` в кассовые ветки и добавляет read-only диагностику `scripts/diagnose-guest.mjs`. Для уже обработанных production-строк требуется сначала изучить результат диагностики. Не удалять `bonus_grants` и не запускать ручное восстановление вслепую.

## Runbook: ручная отправка одного сообщения

1. Найти профиль по Telegram ID в базе и убедиться, что совпадение ровно одно.
2. Использовать внутренний `customers.id` как первый аргумент `sendTg(cid, title, body, markup)`. Не передавать туда Telegram chat ID.
3. Для первого теста отправлять только на свой профиль. Не менять бонусы ради проверки отправки.
4. Проверить возвращённый результат и серверный лог. В версии с PR #63 при успехе должен быть доступен `messageId`; `no_tg`, `no_token`, `telegram_api_error` и `network_error` означают, что успешная отправка не подтверждена.
5. Для проверки доставки адресату убедиться, что сообщение видно в его чате. Лог API не подтверждает прочтение.
6. Для массовой рассылки сначала сформировать и проверить список получателей, исключить дубликаты и неоднозначные привязки; не выполнять рассылку в том же шаге, что и диагностику.

Пример только для чтения, запускается из корня приложения с его рабочим `.env`:

```bash
node --env-file=.env --input-type=module -e '
import { db } from "./server/db/connection.js";
const tgId = "TELEGRAM_CHAT_ID";
const rows = db.prepare(
  "SELECT id, name, tg FROM customers WHERE CAST(tg AS TEXT) = ?"
).all(tgId);
console.log("MATCHES:", rows.length);
console.log(rows);
'
```

Не вставлять в документацию реальные Telegram ID, токены, номера телефонов или содержимое приватных переписок.
