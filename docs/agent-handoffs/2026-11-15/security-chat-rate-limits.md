# [Handoff][Security] Prevent chat rate-limit storage abuse with forged thread keys

## Проблема

В chat send flow лимитирование по IP/thread выполняется до полной авторизации guest capability. Запросы с синтаксически допустимыми, но выдуманными ключами могут создавать записи в `chat_rate_limits`, даже если последующая проверка доступа отклоняет запрос. Очистка старых записей ограничена возрастом, поэтому остаётся риск накопления мусорных строк в SQLite.

Evidence:
- `server/routes/chat.js` — `applyGuestRateLimits()`
- `server/routes/chat.js` — `authorizeGuestThread()`
- таблица `chat_rate_limits` и её cleanup

## Предлагаемое решение

1. Переставить проверки так, чтобы per-thread rate-limit state создавался только после успешной проверки capability/владения.
2. Сохранить IP-level защиту до дорогих операций, но не создавать запись на каждый произвольный thread key.
3. Добавить ограничение cardinality/retention для таблицы и безопасную очистку.
4. Нормализовать ключи и валидировать их формат до обращения к БД.
5. Проверить конкурентные запросы и поведение при повторных попытках.

## Критерии приёмки

- Неавторизованный запрос с новым forged key не создаёт per-thread запись.
- Валидный guest capability продолжает работать и корректно лимитируется.
- IP-level rate limit не обходится подстановкой новых thread keys.
- Таблица не растёт без верхней границы при длительной работе.
- Есть тесты на forged keys, valid keys, burst/concurrency и cleanup.

## Объём

Только чатовые лимиты и их хранение. Не менять формат guest capability и UX чата без необходимости.

## Примечание

Пороговые значения и retention должны быть обоснованы текущим трафиком. Production-код намеренно не менялся.
