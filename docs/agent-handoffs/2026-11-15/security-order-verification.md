# [Handoff][Security] Enforce verified customer state before order creation

## Проблема

Регистрация может создать профиль без подтверждённого OTP, но вернуть bearer token. При этом создание заказа защищено `userGuard`, который сам по себе не гарантирует, что номер телефона подтверждён. В результате неподтверждённый профиль потенциально может создавать заказы с чужим номером.

Evidence:
- `server/routes/auth.js` — `POST /api/auth/register`
- `server/routes/orders.js` — `POST /api/orders`
- user auth middleware / customer verification state

Важно: ручная активация сотрудником может быть намеренным бизнес-процессом. Перед изменением нужно зафиксировать, какие операции разрешены неактивированному гостю.

## Предлагаемое решение

1. Описать состояния customer: pending/unverified, verified/activated и допустимые переходы.
2. Ввести явную серверную проверку подтверждения номера в точке создания заказа (или отдельный policy middleware).
3. Сохранить нужный onboarding flow: неподтверждённый профиль может завершить только разрешённые действия, но не обходить proof-of-possession.
4. Проверить все способы регистрации/активации: OTP, ручное создание сотрудником, Telegram binding и повторная регистрация.
5. Возвращать клиенту стабильную машинно-читаемую ошибку для неподтверждённого профиля.

## Критерии приёмки

- Неподтверждённый профиль не может создать заказ, если это запрещено утверждённой бизнес-политикой.
- Подтверждённый профиль может создать заказ.
- Ручная активация сотрудником работает по документированному правилу.
- Нельзя получить доступ к существующему customer, просто зарегистрировав чужой номер.
- Есть интеграционные тесты на все переходы статусов и на endpoint создания заказа.

## Объём

Не переписывать весь auth flow. Изменять только необходимые guards, регистрацию/активацию и тесты.

## Примечание

До реализации требуется подтвердить продуктовую политику для заказов pending-профилями. Production-код намеренно не менялся.
