## Контекст

Security-аудит ветки `pizza` от 2026-11-12. В предоставленном описании отчёт указан как `claude/audit-2026-11-12.md`, но файл не найден в текущей ветке GitHub. Поэтому этот PR фиксирует план работ по переданному резюме и отдельно перечисляет находки, подтверждённые чтением текущих файлов `pizza`.

Это **план remediation**, не исправления. Ничего из найденного не считается устранённым.

## Подтверждённые при проверке текущей `pizza`

- `server/routes/auth.js`: `POST /api/auth/setup-pin` принимает телефон и PIN без доказательства владения номером, затем выдаёт bearer-токен. `POST /api/auth/login` также позволяет самостоятельно задать PIN профилю без PIN, используя только знание телефона.
- `server/config.js`: коды ролей имеют fallback `3364`, `2468`, `5719`. Те же значения указаны в `.github/workflows/ci.yml` как тестовые значения; нужно убедиться, что production не принимает fallback.
- `server/routes/chat.js`: `POST /api/chat/send`, `POST /api/chat/botlog` и `GET /api/chat/thread` не используют guard. Клиент выбирает ключ треда; можно писать в произвольный ключ и читать историю по известному ключу. `send` может запускать staff push через `human`.
- `server/routes/auth.js`: неверные попытки `/api/auth/register` не вызывают `registerFail`; `/api/auth/request-otp` имеет только текущую IP-блокировку, но не собственный счётчик/интервал отправок.
- `server.js`: `TRUST_PROXY` применяется только если переменная явно задана. Комментарий к конфигу верен: нельзя вслепую включать `true`; в production за Nginx должен быть указан ровно доверенный hop/адрес, соответствующий реальному сетевому пути. Реальный серверный `.env` здесь не проверялся.
- `server/routes/orders.js`: поля заказа, названия блюд, модификаторы, комментарий, адрес и имя вставляются в HTML-шаблон Telegram с `parse_mode=HTML` без экранирования. Ошибка Telegram API может привести к потере уведомления; нужно тестировать и канал кухни, и чек клиента.
- `server/routes/auth.js`: удаление аккаунта очищает чат только по ключу `<id>`, тогда как чатовый поток допускает суффиксы контекста `:c` и `:d`. Нужна полная очистка связанных ключей и метаданных.

## P0 — закрыть до публикации в App Store / Google Play

### 1. Доказательство владения телефоном до выдачи сессии
- Убрать возможность получить токен через `setup-pin` только по номеру телефона.
- Согласовать единый flow: подтверждённый OTP/Telegram contact или существующая сессия; PIN задаётся только после proof-of-possession.
- Проверить все пути: `login`, `setup-pin`, `check-reg`, `register`, `tg-link`, регистрация/активация гостя кассиром.
- Миграционная совместимость: не заблокировать текущих клиентов и гостевые профили, заведённые персоналом.
- Тесты: чужой номер без подтверждения не даёт токен и не позволяет установить PIN; подтверждённый владелец может задать PIN; существующий PIN нельзя перезаписать анонимно.

### 2. Секреты и коды сотрудников
- Удалить production fallback-коды из `server/config.js`; при отсутствии production-кода сервер должен безопасно отказывать в активации роли или не стартовать с понятной ошибкой.
- Оставить фиктивные значения только в изолированной тестовой конфигурации CI без переиспользования в runtime production.
- Проверить все workflow, тесты, README/runbook и deployment variables на опубликованные значения.
- Сменить все коды, которые могли быть доступны из репозитория/CI.
- Не записывать реальные секреты в PR, логи и документацию.

### 3. Авторизация и изоляция чатов
- Привязать гостевые chat key к аутентифицированному `req.user.id` либо к короткоживущему непрозрачному capability-токену; не принимать произвольный ключ, позволяющий читать чужой тред.
- `botlog` должен быть внутренним серверным контрактом, не публичным произвольным endpoint; убрать публичную возможность писать от имени bot.
- Ограничить отправку сообщений и вызов `human`, защитить массовые push от спама.
- Проверить роль/контекст staff на каждом действии, включая list/dialog/reply/close/open.
- Тесты: чтение и запись в чужой тред невозможны; guest не может имитировать bot/staff; staff видит только разрешённый бренд/контекст; нельзя вызвать push произвольным количеством запросов.

### 4. Brute force, OTP и reverse proxy
- Ввести лимиты на неверные попытки регистрации/проверки кодов и на выдачу OTP отдельно от лимита входа.
- Лимиты должны переживать рестарт процесса и быть scoped по аккаунту/телефону плюс IP; исключить глобальную блокировку всех клиентов.
- Проверить настройки Express `trust proxy` по реальной топологии Nginx → app. Не использовать доверие всем forwarded headers.
- Убедиться, что блокировки не обходятся сменой IP, повторным запросом OTP или перезапуском процесса.
- Тесты: серия неверных кодов получает 429/403 с корректным backoff; новый OTP нельзя запрашивать бесконечно; разные телефоны не блокируют друг друга; X-Forwarded-For spoofing не обходит rate limit.

### 5. Надёжная отправка Telegram-заказов
- Экранировать все динамические поля HTML для обоих уведомлений: кухня/персонал и чек клиента.
- Не позволять некорректному пользовательскому тексту ломать форматирование или скрывать строки заказа.
- Проверять результат `sendPush`/Telegram доставки; ошибка уведомления не должна маскироваться как успешная отправка заказа.
- Отдельно определить retry/outbox-поведение. Не заявлять exactly-once для внешнего уведомления без надёжного transactional outbox.
- Тесты на `<3`, `&`, кавычки и HTML-подобные строки в комментарии, адресе, имени, названии блюда и модификаторе; заказ сохраняется, текст в Telegram безопасен, кухня получает корректную информацию.

### 6. Удаление аккаунта и персональных данных
- Удалять все чаты по базовому ID и его контекстным ключам (`:c`, `:d`), связанные `chat_meta`, сообщения и все push-токены.
- Проверить все места хранения идентификаторов пользователя, включая FCM, Web Push, Telegram binding, логи/историю и временные OTP.
- Сохранить только те данные заказа, которые действительно требуются для учёта/закона; персональные поля должны быть необратимо обезличены.
- Тесты: после удаления профиль, его токены, push-подписки и все chat variants отсутствуют; история не раскрывается по прежнему ключу; заказ остаётся только в согласованном обезличенном виде.

## P1 — оставшиеся проверки аудита

### 7. Токены и сессии
- Проверить `server/domain/helpers.js` / middleware: срок жизни токена, отзыв при logout/delete, ротация и хранение.
- Ввести exp/TTL и миграцию без массового разлогина без необходимости.
- Проверить все выдающие токен endpoints и долгоживущие ссылки `auth_token`.

### 8. Lockout / OTP state
- Проверить хранение `pinLocks` и `otpStore`: память процесса, рестарты, очистка просроченных записей, cardinality и возможность DoS.
- Добавить persistence/TTL только в объёме, необходимом для корректной защиты; не строить отдельную платформу лимитов без нужды.

### 9. CI и lockfile
- Проверить, зачем workflow запускает `npm install --package-lock-only` перед `npm ci`. Воспроизводимая сборка должна использовать committed lockfile и не менять dependency graph на лету.
- Не подменять lockfile внутри CI/deploy. При изменении зависимостей lockfile коммитится разработчиком отдельным diff.

### 10. Deployment provenance
- Deploy должен публиковать точный commit SHA, прошедший обязательные checks, а не просто текущий `origin/pizza`.
- В workflow проверить защиту от ручного деплоя непроверенного HEAD, rollback и отображение deployed SHA.
- Текущий `deploy.yml` использует `git reset --hard origin/pizza`; это требует отдельного решения о workflow_dispatch и provenance.

### 11. Test mode / DB path
- Удалить определение тестового режима по подстроке `tmp` в `DB_PATH` из `server/routes/orders.js`.
- Использовать только явный `NODE_ENV=test` или отдельный флаг, допустимый в тестовом окружении.
- Тест: production DB path с `tmp` в имени не отключает бизнес-ограничения.

### 12. Telegram webhook
- Повторно проверить webhook secret, обработку дубликатов update_id, replay, порядок ACK/обработки, ошибки и таймауты.
- Текущий код проверяет `X-Telegram-Bot-Api-Secret-Token` и отказывает, если секрет не задан; это подтверждено. Остальные свойства нужно проверить тестами.

### 13. Создание клиента сотрудником
- Повторно пройти `POST /api/staff/customers` и `createCustomer`: валидация телефона/имени, проверка дубликатов, побочные эффекты, активация и выдача бонусов.
- Зафиксировать контракт для уже существующего неактивированного профиля и исключить нежелательную верификацию/бонус при конфликте.

### 14. Capacitor / store release
- Проверить `capacitor.config.json`, AndroidManifest, Info.plist, AppDelegate/SceneDelegate, permissions, backup, ATS/cleartext policy, app identifiers, push capabilities и release/debug flags.
- Текущий `capacitor.config.json` задаёт `appId=app.andcoffee`, `appName=И кофе...`, `webDir=public`; Android manifest разрешает backup и запрашивает INTERNET/CAMERA; iOS Info.plist содержит `CAPACITOR_DEBUG`. Это не является полным store compliance review.
- Проверить privacy manifest / required-reason APIs, privacy policy URL и удаление аккаунта в приложении с учётом текущих правил магазинов.

### 15. Stored XSS в интерфейсах персонала
- Проверить весь staff render path чата и заказов, включая cashier/admin/dispatch.
- В `public/app/chat.js` гость и staff диалог выводят сообщения через HTML templates; часть мест использует `esc()`, но текущая проверка показала URL-linkification в гостевом чате после escaping и staff dialog отдельным шаблоном. Провести полный аудит всех dynamic sinks, атрибутов и URL схем.
- В `public/app/orders.js` карточки используют `innerHTML`; имена/модификаторы/адрес/комментарий частично экранируются, но нужно закрыть все поля и атрибуты (ID, status, pay, slot, no, date) с allowlists/escaping.
- Исправлять на уровне render helper/DOM text APIs там, где это уменьшает риск, не заменять весь UI без необходимости.
- Тесты: payloads в сообщении гостя и comment/name/item fields не создают DOM/script/event handler; безопасные ссылки допускают только http/https.

## Проверки и ограничения аудита

- База PR: `pizza`.
- Ветки/файлы проверять по SHA; Graphify — навигация, его снимок на момент задачи `15f03ff`, подтверждать актуальными файлами GitHub.
- В этом draft не заявляется, что тесты, линтеры, CI, production .env или store review были выполнены.
- Реальный production .env / секреты VPS недоступны в репозитории и требуют отдельной операционной проверки.
- Перед закрытием каждого пункта: тесты до/после, commit SHA, CI run, residual risk и evidence в PR.

## Рекомендуемое разбиение

Не делать один огромный security diff. После согласования плана разделить P0 на небольшие последовательные PR: (1) proof-of-possession, (2) employee secrets, (3) chat authorization/rate limits, (4) rate limit/proxy, (5) Telegram escaping + delivery tests, (6) deletion cleanup + privacy tests. P1 — отдельными PR по затрагиваемым подсистемам.
