# Бонусы: правила, проверка и восстановление

Практическая документация для приветственных бонусов, персональной бесплатной доставки и диагностики инцидентов. Источник реализации: `server/domain/bonuses.js`, `server/utils/bonus-config.js`, `server/domain/loyalty.js`.

## Бизнес-правила

### Каналы начисления

| Вид | Событие | Ограничения |
| --- | --- | --- |
| `signup` | Обычная регистрация | Только подтверждённый профиль гостя |
| `qr` | Регистрация по QR-постеру | Только подтверждённый профиль гостя |
| `install` | Установка приложения | Отдельный вид бонуса; не является вторым приветственным бонусом |

`signup` и `qr` — альтернативные каналы одного приветственного бонуса. Получение через один канал закрывает возможность повторного приветственного начисления через другой. Повторный вызов не должен создавать вторую запись начисления или вторую запись истории.

Для `signup`/`qr` проверяется, что профиль действительно новый: предыдущие начисления, чашки, штампы, доступный подарок, история прежнего приветственного начисления или использованный персональный промокод могут означать, что бонус уже не положен. Бонусы выдаются только подтверждённым профилям с ролью гостя.

### Что выдаётся по умолчанию

Настройки находятся в `meta.bonus_cfg`; значения по умолчанию определены в `server/utils/bonus-config.js`. Для `signup` и `qr` стандартная конфигурация:

- **Кофейня:** 10 штампов. Десять штампов автоматически превращаются в один бесплатный напиток: остаток штампов становится 0, `customers.free` увеличивается на 1.
- **Доставка:** одна бесплатная доставка. Создаётся персональный промокод `kind='freeship'`, привязанный к клиенту, с лимитом использования 1 и сроком действия из настройки `days` (по умолчанию 30 дней). При применении обнуляется стоимость доставки, а не сумма товаров.

Это не означает, что в `customers.cups` прибавится 10: `cups` — счётчик фактически выданных через кассу чашек; приветственные штампы записываются в `stamps/free`.

### Где хранится состояние

- `bonus_grants` — идемпотентные отметки вида начисления (`cid`, `kind`, `ts`).
- `customers.stamps` — текущие штампы карты.
- `customers.free` — доступные бесплатные напитки.
- `promos` — промокоды, срок действия, владелец, область действия и число использований.
- `history` — пользовательская история начисления и списания.
- `meta.bonus_cfg` — конфигурация бонусов.

Наличие отметки в `bonus_grants` само по себе не доказывает, что бонус реально выдан, если отметка создана ошибочной миграцией/backfill. С другой стороны, удалять отметки без расследования опасно: можно выдать бонус повторно.

## Проверки

### Автоматические тесты

Локальные unit/integration-тесты:

```bash
npm run test:unit
```

Playwright E2E:

```bash
npx playwright test tests/bonus-lifecycle.spec.js --project=chromium
npx playwright test tests/bonus-signup.spec.js
```

В CI сценарий `Bonus Lifecycle E2E` запускается отдельным gate в workflow `.github/workflows/ci.yml`. Playwright поднимает локальный сервер с `NODE_ENV=test` и отдельной SQLite-базой `.playwright-test.db`; эта база не должна быть production-базой.

Тестовый OTP-маршрут `POST /__test/otp` регистрируется только при `NODE_ENV=test`. Не включать тестовый режим в production и не добавлять тестовый маршрут в production-конфигурацию.

Покрытые E2E-сценарии:
1. Подтверждённая регистрация выдаёт приветственный бонус.
2. Повторная регистрация с тем же номером отклоняется.
3. QR-регистрация выдаёт тот же вид приветственного бонуса ровно один раз.
4. Персональный код бесплатной доставки доступен до использования.
5. Первый заказ применяет код, после чего код больше не доступен; повторное применение отклоняется.

### Ручная проверка профиля

Используйте только внутренний ID клиента (`customers.id`) и не публикуйте персональные данные в логи/тикеты. Проверять следует в таком порядке:

1. Найти профиль и убедиться, что это нужный подтверждённый гость.
2. Проверить записи `bonus_grants` по этому клиенту и отличить фактическое начисление от исторического backfill.
3. Сопоставить `customers.stamps/free/cups` с историей начислений.
4. Проверить наличие персонального промокода `freeship`, его `owner`, `active`, `expires`, `uses/maxuses` и область действия `delivery`.
5. Убедиться, что повторное начисление не произойдёт, и только затем решать, требуется ли восстановление.

Endpoint `GET /api/me/free-delivery` доступен авторизованному клиенту и возвращает `{ code }`: активный персональный код либо `null`.

## Безопасное восстановление production-начисления

Скрипт `scripts/repair-bonus-grants.mjs` предназначен для точечного восстановления клиента, у которого приветственный бонус был заблокирован доказанно ложными отметками backfill.

**Сначала только чтение (dry-run). Не запускайте `--apply` для класса `unclear` или `real`. Массового применения намеренно нет.**

Команды выполнять из `/var/www/app` на сервере. Для production-базы явно указывайте `/var/www/data/zerno.db`; не подменяйте её файлом `/var/www/app/zerno.db`.

Аудит затронутых записей без изменения базы:

```bash
node --env-file=/var/www/app/.env scripts/repair-bonus-grants.mjs \
  --db /var/www/data/zerno.db --affected
```

Dry-run для одного клиента:

```bash
node --env-file=/var/www/app/.env scripts/repair-bonus-grants.mjs \
  --db /var/www/data/zerno.db --cid <CUSTOMER_ID>
```

Применение возможно только после проверки оснований, для одного клиента и с резервной копией:

```bash
node --env-file=/var/www/app/.env scripts/repair-bonus-grants.mjs \
  --db /var/www/data/zerno.db --cid <CUSTOMER_ID> --apply
```

Добавляйте `--notify` только если требуется отправить уведомление этому клиенту после успешного коммита. `--notify` не нужен для обычной диагностики.

Скрипт проверяет предусловия, делает SQLite backup, проверяет целостность копии, выполняет изменение транзакционно и сверяет ожидаемое состояние. Если проверка не пройдена, операция должна остановиться или откатиться. Не удаляйте записи `bonus_grants` вручную и не запускайте скрипт повторно «на всякий случай».

### CLI и Telegram

CLI-скрипт, которому нужен Telegram-токен, следует запускать с загрузкой проектного env-файла:

```bash
node --env-file=/var/www/app/.env ...
```

Иначе CLI-процесс может вернуть `no_token`, хотя запущенное через `node --env-file=/var/www/app/.env server.js` приложение работает. Не выводите токен в терминал, логи или тикеты. Успешный ответ Telegram Bot API подтверждает принятие сообщения API, но не прочтение сообщения пользователем.

Был выполнен точечный repair для подтверждённого кандидата, проверена целостность резервной копии и состояние после начисления; сообщение было отдельно отправлено через CLI с загрузкой `.env`. Конкретные customer ID, номера телефонов, Telegram ID и коды промокодов намеренно не фиксируются.

## Чек-лист после изменения логики бонусов

- [ ] Обновлены unit-тесты на идемпотентность и взаимное исключение `signup/qr`.
- [ ] Проверены настройки по умолчанию и переопределённая `meta.bonus_cfg`.
- [ ] E2E запускается на изолированной тестовой SQLite-базе.
- [ ] Проверены выдача бесплатного напитка и одноразовая бесплатная доставка.
- [ ] В CI зелёны отдельный bonus lifecycle gate и остальные Playwright-тесты.
- [ ] Перед production repair выполнены dry-run, проверка классификации клиента и резервная копия.
- [ ] После изменения проверены история, остаток бонуса и промокод; не опубликованы персональные данные.
