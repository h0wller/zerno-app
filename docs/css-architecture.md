# CSS-архитектура «…и кофе × Пятница»

## Область и модель

Этот документ описывает фактический контракт CSS в текущем Vanilla JS приложении. Архитектура состоит из четырёх логических слоёв ответственности; второй разделён на 2а (токены) и 2б (runtime CSS). `public/index.html` также содержит загрузочный контур и critical CSS первого кадра — эти механизмы относятся к слою 4, но их роли различны.

Логический номер слоя не равен порядку фактического применения каждого правила: CSS cascade определяется порядком подключения, специфичностью, происхождением и состоянием. Runtime-инъекция из `core/views.js` появляется после загрузки ESM-модуля; inline critical CSS существует до внешних stylesheet. Поэтому любое перемещение правила требует проверки computed styles и первого кадра в браузере.

## Слой 1 — базовый UI: `public/app/ui/theme/*.css` и `public/app/ui/fonts.css`

Содержит общую геометрию и нейтральную базу компонентов: reset, типографику, сетки, карточки, кнопки, поля, панели, модалки, рейлы, состояния и responsive-правила.

Ограничения:
- Не использовать `!important`, кроме системной защиты для `[hidden]`.
- Не размещать брендовые селекторы `[data-brand="..."]`.
- Не хардкодить известные брендовые цвета «Пятницы»; использовать значения из семантических tokens. Точный список значений, которые статически ищет аудит, поддерживается в `scripts/css-audit.mjs` и не является исчерпывающим анализом всех возможных цветов.
- Не создавать повторный патч в конце файла вместо редактирования канонического правила.
- Повтор одного селектора в базовом и media/state-контексте может быть корректной responsive-послойностью; смотреть на контекст, а не только на текст селектора.

## Слой 2а — брендовые данные: `public/app/ui/brand-tokens.css`

Содержит только custom properties для брендовых корней: `html[data-brand="..."]` и `body[data-brand="..."]` (в том числе допустимые парные селекторы). Каждая декларация должна быть переменной `--*`, без `!important`.

Запрещены обычные CSS-свойства, component selectors, layout и состояния. Брендовые значения задаются здесь, а runtime-правила их потребляют.

## Слой 2б — runtime layout и brand overrides: `public/app/core/views.js`

`views.js` создаёт единый `<style>` из массива `rules` и добавляет его в `document.head`. Это централизованный слой для:
- runtime/system/layout-правил оболочки, media queries и safe-area;
- брендовых переопределений под `[data-brand=...]`;
- небольших правил состояний/совместимости, принадлежащих coordinator-у видов.

`views.js` также управляет переключением видов и отдельными DOM-переездами (см. `docs/module-map.md`). Это не означает, что любой DOM/layout код автоматически должен находиться в его CSS-массиве: размещение каждого правила определяется конкретным owner и существующей каскадной моделью.

Не все правила здесь обязаны иметь брендовый префикс. Действующий аудит (`scripts/css-audit.mjs`, Rule 4) разрешает явно перечисленные общие layout/system-селекторы, ID-селекторы, media/keyframes и правила с `[data-brand]`. Список разрешений в аудите — это фактический enforcement, а не универсальное разрешение размещать в views любой CSS.

Инварианты:
- Не определять custom properties в `views.js`; их источник — `brand-tokens.css`.
- Использовать токены для брендовых значений, не разносить hardcoded brand colors.
- Не добавлять inline `!important` страховки.
- Сохранять лимит `[data-brand]=` вхождений не выше 85. Текущее условие подсчитывает число вхождений этой подстроки в извлечённой CSS-строке, а не сложные CSS-селекторы как AST-единицы.
- Не дублировать селекторы внутри массива `rules`.
- Переносить правило между theme и views только после проверки DOM ownership, media-контекстов, порядка/специфичности и соответствующих тестов.

## Слой 3 — стили компонентных модулей

Включает локальные динамические инъекции CSS в модульных владельцах (например, `delivery.js`, `ui/styles.js` и отдельные UI-модули). Используется для состояния конкретного компонента, локальной анимации и поведения, которое не должно становиться глобальной базой.

Нельзя:
- изменять отсюда базовые правила theme или общие брендовые токены;
- создавать второй writer для чужого компонента/DOM;
- хардкодить брендовые цвета вместо custom properties;
- вводить новую глобальную геометрию без решения о владельце и обновления документации.

## Слой 4 — HTML first-frame: `public/index.html`

Внутри этого слоя есть два разных механизма.

### Critical inline CSS

Inline styles в head нужны только для предотвращения FOUC и стабилизации первого кадра (в частности, шапки, марки, сетки, splash и зарезервированных областей). Некоторые правила явно зеркалируют более поздние canonical theme styles: комментарий должен указывать исходный файл, а обе копии должны обновляться вместе. Не добавлять сюда полный компонентный UI.

### Внешние stylesheets и fallback

Основной документ содержит:
- fonts stylesheet;
- по одному stylesheet link на каждый theme CSS-файл в числовом порядке;
- brand tokens после theme;
- эквивалентный список ссылок в `<noscript>`.

Основные ссылки используют неблокирующий `media="print"` с переключением на `all` через `onload`; `<noscript>` даёт обычные синхронные stylesheet links при отключённом JS. На базовом коммите текущие stylesheet query versions синхронизированы с `STATIC_CACHE` (номер версии не фиксируется в этом документе). Не менять стратегию загрузки, порядок или число подключений не проверив Safari, PWA и Telegram WebView, deferred CSS и CLS.

## Фактическое подключение и проверка

Источники текущего поведения:
- `public/index.html`: stylesheet links, noscript fallback, critical CSS.
- `public/app/main.js`: ESM imports; `core/views.js` загружается как модуль, а runtime style инжектируется при выполнении модуля.
- `public/app/core/views.js`: массив runtime `rules`, добавляемый к `document.head`.
- `scripts/css-audit.mjs`: статические проверки theme, brand tokens и извлекаемого массива rules.
- `scripts/brands-check.mjs`: проверка брендового token/asset контрактов.
- `scripts/bump-sw.mjs`: синхронизация `STATIC_CACHE` и query-version CSS/fonts/bundle в `index.html`.

### Что реально проверяет `scripts/css-audit.mjs`

Аудит:
1. Считывает все `theme/*.css` в естественном числовом порядке.
2. Проверяет `!important` в theme, разрешая его только в `[hidden]`.
3. Запрещает `[data-brand=...]` в theme и известные hardcoded Friday colors.
4. Извлекает массив `rules` из `views.js` регулярным выражением и допускает перечисленный в скрипте набор layout/system/media/brand selectors.
5. Проверяет баланс фигурных скобок theme (это не полноценный CSS parser).
6. Проверяет ряд известных разрывов/опечаток в извлечённом views CSS.
7. Проверяет отсутствие повторяющихся селекторов в массиве `rules`.
8. Делает ограниченные структурные проверки извлечённого CSS (в том числе пустые строки/висячие media/комментарии, дубли selector strings и ограниченный набор критических пересечений) и проверяет пересечения с ограниченным набором селекторов critical FOUC guard. Это не полноценное сравнение всех inline и external CSS правил.
9. Проверяет, что `brand-tokens.css` содержит только custom properties в разрешённых brand-root selectors.
10. Запрещает определения custom properties в views CSS.
11. Запрещает inline logo-style workaround, удалённый в прежней фазе.
12. Ограничивает количество брендовых правил значением 85.
13. Мониторит повторы селекторов в theme в режиме предупреждения; корректную responsive-послойность не считает настоящим дублем.

Проверка theme-дубликатов работает в warning-mode: повторения сопоставляются по базовому селектору и контексту `@media`; послойность responsive/state не считается ошибкой. Проверка дублей в `views.js` проще: ищет повторяющиеся selector strings по извлечённым строкам, без построения CSS AST.

Аудит запускается через `npm run pretest` (см. `package.json`). Его зелёный результат не означает, что проверены полная CSS grammar, все конфликты между любыми источниками, computed styles, браузерные различия или визуальная точность. Для этого нужны Playwright/browser checks и screenshot comparison.

### Cache-busting

Изменения CSS/fonts и связанных публичных ассетов должны проходить через существующий механизм: `npm run build:client` вызывает `scripts/bump-sw.mjs`, который инкрементирует `STATIC_CACHE` и синхронизирует `?v=` для stylesheet/bundle URLs в `index.html`. Обновление версии выполняется одним механизмом; точный scope задают regex в `scripts/bump-sw.mjs`. Не редактировать номер версии вручную и не считать обычное изменение markdown причиной для cache bump.

## Правила выбора слоя

1. Базовая геометрия/компонент, независимые от бренда → Слой 1.
2. Брендовые значения custom properties → Слой 2а.
3. Runtime/layout coordinator или брендовый селектор, опирающийся на tokens → Слой 2б.
4. Состояние/анимация, принадлежащие конкретному модулю → Слой 3.
5. Только первый кадр до внешних стилей → critical CSS в Слое 4; загрузочный fallback остаётся частью HTML shell.
6. Если правило не укладывается — определить DOM/CSS owner до реализации, не выбирать слой по удобству.

## Регламент изменений

- Правки `public/*` требуют build/cache-busting через существующий `npm run build:client`.
- После стилей запускать CSS/brand/observer audits и релевантные Playwright проверки; визуально сравнивать оба бренда и целевые viewport.
- Проверять slow-network layout, deferred stylesheet application, PWA cold start и Telegram WebView там, где доступна автоматизация.
- Обновлять `docs/module-map.md` вместе с любым изменением DOM ownership или модуля-владельца runtime injection.
