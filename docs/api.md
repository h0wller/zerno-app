# API zerno-app

Краткий маршрутный справочник, сверенный с `server.js` и `server/routes/*.js` на ветке `pizza`. Точные схемы запроса/ответа, auth и коды ошибок см. в [OpenAPI 3.0](./openapi.yaml).

## Авторизация и guards

- Bearer-токен: `Authorization: Bearer <token>`.
- **Срок пользовательской сессии:** сервер выдаёт bearer-токен на 30 дней от момента выпуска. Срок абсолютный и не продлевается обращениями к API; после наступления срока все пользовательские и ролевые guards отклоняют токен с `401`. Legacy-токены мигрируются от исходного `tokens.ts`; некорректные даты считаются истёкшими. `POST /api/exit` отзывает текущую сессию, `DELETE /api/me` отзывает все сессии профиля.
- `userGuard` — авторизованный пользователь.
- `staffGuard` — кассир или администратор.
- `dispatchGuard` — кассир, диспетчер или администратор; очередь заказов и операции диспетчеризации доступны всем трём ролям.
- `menuGuard` — кассир, диспетчер или администратор; для не-администраторов `PUT /api/menu/:id` разрешает только переключение `on` в собственной секции (кассир — coffee, диспетчер — delivery).
- `chatGuard` — кассир, диспетчер или администратор; кассир видит кофейные треды, диспетчер — delivery-треды.
- `adminGuard` — администратор.
- Доступ следует проверять по middleware в конкретном роутере. Пометка «по реализации» означает, что краткая таблица намеренно не выводит роль только из названия пути.
- `POST /__test/otp` подключён только при `NODE_ENV=test`; это не production API.

## Авторизация и профиль

SMS.ru остаётся подготовленным будущим платным каналом: этот PR не подключает и не включает отправку SMS. В форме регистрации нет SMS-кнопки и поля независимо от `smsAuthEnabled`; отдельный вход по PIN/OTP сохраняет свой существующий контракт. Серверная интеграция SMS не меняется.

| Метод и путь | Назначение | Примечание |
|---|---|---|
| `POST /api/auth/request-reg-otp` | Начать регистрацию через Telegram-бота | PWA: `phone`, `name`, 4-digit `pin`, `consent=true`, `via=tg`, `returnTo` обязателен; legacy-вызовы без `returnTo` сохраняют прежний контракт. Возвращает `tgUrl`, одноразовый `pollToken`, `expiresAt`; бот проверяет собственный контакт; возвращение идёт на исходный путь/экран; browser-session выдаётся только через `check-reg` |
| `POST /api/auth/check-reg` | Завершить регистрацию Telegram в исходной PWA-сессии | Body `pollToken`; одноразовый ключ выдаётся только браузеру инициировавшего запроса, по номеру телефона его получить нельзя; после подтверждения возвращает токен и профиль один раз |
| `POST /api/auth/register` | Создать профиль и завершить регистрацию | Имя, телефон, согласие, `code?`; OTP подтверждает номер и сразу активирует профиль; без кода профиль ожидает активации сотрудником и не может оформить заказ; лимит ошибок по телефону и IP |
| `POST /api/auth/tg-link` | Вход или привязка по подписанному Telegram initData | Может вернуть `needPhone` или `needBotConfirm` |
| `POST /api/auth/login` | Вход по телефону и PIN либо одноразовому коду | PIN или OTP; успешный OTP подтверждает номер и активирует pending-профиль; вход по PIN не меняет состояние подтверждения; SMS-OTP принимается только при `SMS_AUTH_ENABLED=true` |
| `POST /api/auth/request-otp` | Запросить входной OTP | `phone`; Telegram — основной канал, SMS fallback только при `SMS_AUTH_ENABLED=true`; иначе при недоступном Telegram возвращается `503`; лимиты по IP и номеру |
| `POST /api/auth/setup-pin` | Первичная установка PIN в уже подтверждённой сессии | `pin`; требует `userGuard`, не выдаёт токен и не принимает телефон как доказательство владения |
| `POST /api/auth/set-pin` | Сменить PIN текущего профиля | `pin`; userGuard |
| `POST /api/auth/activate-guest` | Активировать профиль кодом кассира | `code`; userGuard; пять неверных попыток блокируют новые проверки на период backoff, ответ `429` |
| `POST /api/auth/tg-link/request` | Получить одноразовую ссылку для активации текущего ожидающего профиля в Telegram | userGuard; только guest с `verified=0`; `returnTo` — относительный путь на исходный профиль; срок 10 минут; Telegram-пользователь должен поделиться собственным контактом с совпадающим номером; bearer-токен не передаётся в ссылке |
| `POST /api/auth/activate` | Войти в режим сотрудника по секрету роли | `code` длиной 16–64 символа; userGuard; секрет берётся только из `ADMIN_CODE`/`CASHIER_CODE`/`DISPATCH_CODE` окружения |
| `POST /api/staff/activate-guest` | Активация ожидающего гостя сотрудником | pendingGuard |
| `GET /api/staff/pending` | Гости, ожидающие активации | pendingGuard |
| `POST /api/auth/deactivate` | Деактивировать режим сотрудника | Авторизованный пользователь |
| `POST /api/exit` | Завершить текущую сессию | Авторизованный пользователь |
| `GET /api/me` | Текущий профиль | userGuard |
| `PUT /api/me` | Изменить имя профиля | userGuard |
| `DELETE /api/me` | Удалить профиль и персональные данные с предусмотренной деидентификацией заказов | userGuard; сотрудник не удаляет собственный профиль |
| `PUT /api/me/notify` | Изменить настройки каналов уведомлений | userGuard |

Коды ролей сотрудников: от 16 до 64 символов из `A–Z`, `a–z`, `0–9`, `_` и `-`. Сервер не подставляет значения по умолчанию; при пустом или слишком коротком env-секрете активация роли отклоняется. Значения кодов в этом документе не хранятся.

## Заказы

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /api/orders` | Создать заказ | `verifiedCustomerGuard`: гость должен иметь `verified=1`; иначе `403 CUSTOMER_NOT_VERIFIED`; разрешённые роли персонала могут оформлять служебные заказы независимо от гостевого OTP-статуса |
| `GET /api/orders` | Очередь заказов для персонала: без `status` — последние три дня; с `status` — до 50 заказов этого статуса без ограничения по дате | dispatchGuard (cashier, dispatch, admin); фильтры `status`, `staff`, `done` |
| `GET /api/orders/mine` | История заказов текущего пользователя | userGuard |
| `POST /api/orders/:id/status` | Изменить статус заказа | dispatchGuard |
| `POST /api/orders/:id/delay` | Задержать один заказ; обязательный `min` — целое число 1–180, `comment` необязателен (до 140 символов) | dispatchGuard |
| `POST /api/orders/delay-all` | Задержать активные обычные заказы и предзаказы на сегодня (будущие предзаказы не затрагиваются); `min` — целое 1–180 | dispatchGuard |

Заказ использует серверную идемпотентность через optional `client_order_id` и fingerprint запроса. Клиентская блокировка кнопки не заменяет серверную защиту. Идемпотентность создания заказа не означает exactly-once доставку внешних уведомлений. Записи позиций в `GET /api/orders/mine` дополнительно содержат `oi` — индекс выбранного варианта меню; у заказов, созданных до этого поля, клиент восстанавливает индекс по сохранённым названию/размеру/цене варианта.

## Чат

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /api/chat/send` | Сообщение гостя и вызов сотрудника | BearerAuth с проверкой владельца треда либо анонимная capability в `X-Chat-Access-Token` |
| `POST /api/chat/botlog` | Сохранить ответ локального бота | Та же проверка владельца/анонимной capability |
| `GET /api/chat/thread` | Получить до 100 новых сообщений треда; пока тред не создан первым сообщением, владелец получает `{ msgs: [] }` | Та же проверка владельца/анонимной capability; query `key`, необязательный `after` |
| `GET /api/chat/list` | Список обращений сотрудника с фильтрацией по бренду | chatGuard |
| `GET /api/chat/dialog` | Получить сообщения существующего диалога сотрудником | chatGuard + проверка бренда |
| `POST /api/chat/reply` | Ответить гостю в существующем диалоге | chatGuard + проверка бренда |
| `POST /api/chat/close` | Закрыть существующий диалог | chatGuard + проверка бренда |
| `POST /api/chat/open` | Переоткрыть существующий диалог | chatGuard + проверка бренда |

**Ключи доступа.** Пользовательский тред имеет формат `u{10 hex}:c` или `u{10 hex}:d` и доступен только при совпадении ID из Bearer-сессии с владельцем. Анонимный ключ имеет формат `anon-{64 hex}:c|d`; запросы к нему требуют отдельный 256-битный токен в заголовке `X-Chat-Access-Token`. Хэш токена хранится в SQLite, сам токен не передаётся в URL. Старые анонимные ключи с коротким случайным суффиксом больше не принимаются — клиент создаёт новый анонимный тред.

**Ограничения.** Текст — 1–2000 символов. За 60 секунд: `send` — до 30 запросов/IP и 10/тред, `botlog` — до 60/IP и 20/тред, `thread` — до 120/IP и 60/тред. IP-лимит выполняется до авторизации как ранний барьер; per-thread счётчик создаётся только после успешной проверки владельца или anonymous capability. Хранилище `chat_rate_limits` очищает записи старше 7 дней и ограничено 20 000 строками; при заполнении новые лимитные идентификаторы отклоняются с `503` (`CHAT_RATE_LIMIT_STORAGE_FULL`) без удаления активных IP-счётчиков. История ограничена 500 последними сообщениями на тред, один ответ poll — максимум 100 сообщений. Для анонимного чата вызов сотрудника недоступен, пока пользователь не войдёт в профиль.

## Push

Все каналы используют один `sendPush` contract: `text` — plain text для Web Push/FCM, `html` — Telegram HTML. Успешная передача в Telegram не маскирует отсутствие доставки на устройство в `/api/push/test`. Logout удаляет Web Push subscriptions и FCM tokens.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /api/vapid` | Публичный VAPID-ключ | Публичный |
| `POST /api/push/subscribe` | Создать или обновить Web Push подписку текущего устройства | userGuard |
| `POST /api/push/test` | Тестовая отправка; `ok: true` только при подтверждённой передаче Web Push или FCM, иначе HTTP 503. Внутренний заголовок `x-smoke-test: 1` не отправляет push и возвращает `{ ok: false, skipped: 'smoke-test' }` | userGuard |
| `POST /api/push/fcm` | Upsert FCM-токена; повторная регистрация переносит token к текущему профилю | userGuard |
| `GET /api/push/subs` | Данные push-подписок | adminGuard |
| `POST /api/push/send` | Административная отправка push | adminGuard |
| `POST /api/push/send-hours-update` | Уведомление об изменении расписания доставки | adminGuard |
| `POST /api/push/unsubscribe` | Удалить только переданный Web Push endpoint и/или FCM token текущего устройства; пустое тело — 400. Logout повторяет точечную очистку через `/api/exit` | userGuard |
| `POST /api/push/del` | Удалить Web Push и FCM device registrations профиля `cid` | adminGuard |

## Статистика

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /api/stats` | Общая статистика | adminGuard |
| `GET /api/stats/redeems` | Списания бесплатных напитков за 30 дней по умолчанию; `?month=YYYY-MM` — календарный месяц в часовом поясе `Europe/Kaliningrad`, с разбивкой по напитку, дням и кассовым начислениям штампов | adminGuard |
| `GET /api/stats/orders` | Статистика заказов | adminGuard |

**JSON body parser.** Обычные API-маршруты используют общий лимит JSON-тела 10 MiB. Некорректный JSON возвращает HTTP 400 `{ error: "Некорректный JSON", code: "INVALID_JSON" }`; тело больше лимита — HTTP 413 `{ error: "Тело запроса слишком большое", code: "PAYLOAD_TOO_LARGE" }`. Сырой запрос и внутреннее сообщение парсера клиенту не возвращаются. Исключения с отдельными лимитами и локальными ответами — `POST /api/clientlog` (4 KiB) и `POST /api/menu/upload` (6 MiB).

## Сверка и ограничения

- Старые пути `POST /api/auth/otp-send` и `POST /api/auth/otp-verify` отсутствуют. Для Telegram-регистрации используются `request-reg-otp` и `POST check-reg` с отдельным случайным `pollToken`; входной OTP отправляется через `request-otp` и проверяется в `POST /api/auth/login`.
- `GET /api/me/free-delivery` существует в `server/routes/promos.js`; он не является устаревшим маршрутом.
- `POST /__test/otp` существует только при `NODE_ENV=test` и не должен считаться публичным API.
- Краткая таблица не перечисляет все поля и коды ошибок. Для request/response схем используйте `docs/openapi.yaml`; при расхождении проверяйте `server.js` и `server/routes/*.js`.
- Изменение любого маршрута требует обновить эту таблицу, OpenAPI и соответствующие contract tests в одном PR.
