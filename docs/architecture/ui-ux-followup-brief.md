# UI/UX follow-up: проверяемые улучшения после аудита

> Основано на аудите от 2026-11-03 и сверке source snapshot `4bd2fd3` в `h0wller/zerno-app`.
> Это концепт для обсуждения и последующего design draft, а не разрешение на реализацию runtime-правок.

## 1. Обзор

Цель следующего этапа — сделать каталог и рабочие режимы понятнее, не меняя принятые продуктовые паттерны и не создавая новый слой CSS. Уже реализованные в PR #130 изменения корзины и подписей цен считаются базой, а не новым объёмом работ. Первым шагом должны стать воспроизводимые тесты и устранение дрейфа документации; UI-изменения допускаются только после того, как тест или наблюдение подтвердит конкретное препятствие.

## 2. Цели

1. Пользователь без мышления «как устроено приложение» понимает, какая категория каталога выбрана, как её изменить и где находится нужный товар.
2. Пользователь может выбрать вариант продукта, увидеть полное значение варианта и цену, добавить его, скорректировать количество и открыть корзину без потери контекста.
3. Сотрудник видит доступные ему рабочие режимы и однозначно понимает активный режим и путь обратно в гостевую витрину.
4. Оба бренда остаются визуально различимыми, а общие компоненты сохраняют общие поведенческие контракты.
5. Изменения не добавляют конкурирующих CSS-владельцев, лишних абстракций или зависимостей.

## 3. Не-цели

- Не заменять вертикальный мобильный рейл горизонтальным списком.
- Не менять основной паттерн header, rail, карт или drawer без сравнимого прототипа и подтверждения проблемы.
- Не переписывать checkout и pricing из PR #130.
- Не переписывать `views.js`, `delivery.js` или CSS целиком.
- Не добавлять компонентную библиотеку, новый UI framework или CSS framework.
- Не менять бэкенд, схему БД, права доступа, бонусные правила, delivery zone logic или расписание.
- Не смешивать refactor/documentation cleanup с пользовательскими функциями.

## 4. Зафиксированные ограничения и решения

### Принятые решения

- Вертикальный rail на мобильных экранах является намеренным продуктовыми решением, зафиксированным в [docs/frontend-todo.md: F5.14–F5.19; product decision 2026-09-28]. Его нельзя менять только потому, что колонка 80 px кажется широкой.
- Расчёт позиции rail в viewport реализован в [public/app/ui/scrolltop.js: alignRailWithCard, updateRailStickyPosition] и тестируется на 320/390/768/1440 px для обоих брендов в [tests/menu-header-rail-layout.spec.js].
- PR #130 уже реализовал денежную детализацию корзины, понятность скидок и отсутствие guessed place. Не возвращать прежний auto-default address/min-order behaviour.
- `cart.js` остаётся единственным владельцем qty/save mutations; `delivery.js` владеет выбором вариантов и добавлением к корзине. Не делать второй writer.
- Обязательные правила из [PROJECT_RULES.md]: минимальный diff, обе марки, никаких новых MutationObserver без согласования, EventBus для межмодульных событий, `main.js` только static imports, `boot.js` последний, `npm run pretest` перед фиксацией, обновление STATIC_CACHE при публичных изменениях, обновление `docs/module-map.md` при изменении модульных контрактов.

### Неразрешённые расхождения

Описание CSS-архитектуры в [PROJECT_RULES.md], [docs/css-architecture.md], [docs/module-map.md] не полностью согласовано с фактическими правилами [scripts/css-audit.mjs], загрузкой [public/index.html: #critical-css] и владельцами в theme modules. Это нужно решить до CSS-реорганизации. До решения runtime layout не трогать.

## 5. Пользовательские сценарии и гипотезы

### H1. Навигация каталога на мобильных устройствах

**Проблема, которую нужно проверить:** пользователю не всегда очевидно, что вертикальный список категорий имеет собственную прокрутку и какая категория выбрана после перехода/скролла каталога.

**Факты:** `#rail` и `#deliveryRail` строятся отдельно; кнопка выбранной категории получает `.on`; rail использует `overflow-y:auto` и скрывает стандартный scrollbar. Геометрия и scroll centering покрыты `menu-header-rail-layout.spec.js`.

**Гипотеза улучшения:** сохранить вертикальный rail и его размеры; добавить/уточнить семантическое состояние активной категории (`aria-current` или `aria-pressed`, выбрать по подходящему ARIA pattern) и проверить, что длинный rail можно заметить и прокрутить на коротком viewport. Не добавлять искусственный gradient/fade до подтверждения, что пользователи не замечают scroll.

**Критерии проверки:**
- На 320×568, 360×640 и 390×844 для двух брендов активная категория визуально и программно однозначна.
- Все категории достижимы скроллом, страница не получает горизонтальный overflow.
- Клавиатура/скринридер позволяют определить выбранную категорию без опоры только на цвет.
- Переход к категории не сбрасывает выбор/фильтры непредсказуемо.
- Существующая проверка rail centering остаётся зелёной.

### H2. Выбор вариантов доставки

**Проблема, которую нужно проверить:** карточки пиццы содержат четыре комбинации размера/теста и четыре плотных кнопки; нужно оценить, насколько легко сравнивать варианты на узком экране, не увеличивая высоту карточки существенно.

**Факты:** `resolveDeliveryAddSelection` требует `.opts button.sel`, цена берётся из выбранной option; добавление сохраняет optionIndex/label/size/price; при отсутствии выбора показывается shake + toast. Эти действия подтверждены [public/app/delivery.js: resolveDeliveryAddSelection, upsertDeliveryCartItem, handleDeliveryAddClick] и [tests/menu-cards.spec.js, tests/cart-regress.spec.js].

**Гипотеза улучшения:** до изменения компонента добавить E2E сценарий, который проверяет, можно ли из accessible name каждого варианта извлечь размер, тесто, вес и цену, и явно проверить состояние выбранной опции. Если проблема подтверждается визуально или в тестировании, сравнить максимум две концепции в изолированном screenshot/mock: текущая compact grid и более явный двухэтапный selector. Не менять модель данных и не создавать новый cart option schema.

**Критерии проверки:**
- Вариант с размером, типом теста, весом, стоимостью доступен по имени и имеет явное выбранное состояние.
- Нельзя добавить товар с options без выбора опции.
- После выбора и добавления правильные option, price, size, qty и line total отображаются в корзине.
- На экранах 320–390 px не возникает обрезания текста, горизонтального overflow или уменьшения touch target ниже 44 px.
- Порядок и цены вариантов остаются соответствующими данным меню, без hardcode.

### H3. Переключатель рабочих режимов

**Проблема, которую нужно проверить:** в зависимости от роли переключатель может иметь от 2 до 4 пунктов; на узком экране он помещается отдельной строкой и допускает горизонтальную прокрутку. Проверить, не теряются ли крайние режимы и всегда ли активный режим очевиден.

**Факты:** список режимов зависит от role в [public/app/core/catalog.js: renderModes]; разрешения режимов подтверждает [public/app/core/views.js: canEnterMode, setMode]; layout `#modeSeg` расположен второй строкой mobile header в [public/app/ui/theme/160-06-delivery-header.css]. Существующий `tests/pour-accessibility.spec.js` проверяет высоту staff header и touch targets, но не полный доступный путь для каждой роли.

**Гипотеза улучшения:** добавить отдельные сценарии для dispatch/cashier/admin и узких экранов; проверить keyboard access, active state, full visibility/scroll of the last mode. Только если тест выявит проблему, сравнить более короткие подписи/альтернативный control pattern. Не объединять действия кассира/диспетчера и не расширять полномочия роли.

**Критерии проверки:**
- Каждый режим виден/доступен только ролям, которым он разрешён.
- Активный режим имеет programmatic state, а не только визуальный класс.
- Горизонтальный scroll не скрывает режим без доступного намёка/возможности навигации.
- Переключение brand и mode не оставляет скрытого/несогласованного представления.
- Не меняется `canEnterMode` и серверная авторизация.

### H4. Согласованность CSS и critical rendering

**Проблема:** документация описывает несколько разных CSS-layer схем, а inline `#critical-css` содержит layout/brand rules, которые затем зеркалируются во внешних стилях. Риск — менять одну сторону и получать FOUC/CLS/регресс на iOS/PWA/TMA.

**Рекомендация:** отдельным документальным PR выбрать один нормативный владелец каждого класса правил, согласовать его с проверками `scripts/css-audit.mjs`, критическим inline CSS, фактической загрузкой theme links и динамической инжекцией. В том же PR обновить `docs/css-architecture.md` и соответствующие разделы `docs/module-map.md`/`PROJECT_RULES.md`, но только после принятия решения владельцем. Не выполнять массовое вырезание дублирующих правил в рамках UX-спринта.

**Критерии проверки:**
- Каждому ключевому selector family (header, wrap, rail, card grid, panel, cart panel) назначен один normative owner и документирован intentional critical mirror, если он нужен.
- Набор правил в документации соответствует `scripts/css-audit.mjs` и фактическому stylesheet order.
- Slow-network, mobile cold-start, iOS/TMA FOUC/CLS checks проходят.
- Нет новых CSS duplicate warnings/селекторных дублей, `pretest` зелёный.

## 6. Риски и способы их снизить

| Риск | Последствие | Контроль |
|---|---|---|
| Изменить принятую модель вертикального rail | Пользовательский паттерн нарушится, переучивание и регресс | Rail pattern остаётся non-goal; изменения только после тестирования |
| Дублировать state между views/catalog/menu | Active state может расходиться с реальным разделом | Использовать существующий `cat`/`dcat` и владельцев |
| Перепроектировать options без проверки данных | Неверный optionIndex, цена или line item | Не трогать schema и использовать текущие helpers |
| Править только theme, забыв critical inline mirror | FOUC/CLS на cold-start и slow network | Отдельный CSS architecture task + visual snapshots |
| Переписывать крупные модули | Непредсказуемый blast radius | Узкие PR, graph impact, linked tests, ponytail review |
| Добавить ARIA к неподходящему pattern | Неверная семантика, мешает клавиатурной навигации | Сначала определить правильную role/pattern; не дублировать implicit ARIA semantics |

## 7. Рекомендуемая последовательность

1. **Documentation alignment (этот PR):** source-grounded карта UI surfaces + brief, без runtime изменений.
2. **UI baseline extension:** небольшие Playwright tests на активное состояние category rails, keyboard/ARIA for options and role modes, 320×568/360×640 mobile views. Не добавлять тесты с ожиданием визуальной гипотезы, если DOM contract не согласован.
3. **Usability comparison:** визуальные screenshot candidates для 1 подтверждённой проблемы (не глобальный redesign); оценить оба бренда.
4. **Implementation PR:** один сценарий/одна проблема; minimal diff; test-before-code contract and screenshots.
5. **Post-merge:** production visual check, cold PWA/TMA check, update `docs/module-map.md` if module ownership changed.

## 8. Открытый вопрос перед runtime design

Какой сценарий должен стать первым полноценным usability-циклом после документационной основы: **выбор варианта пиццы**, **мобильная навигация по категориям** или **переключение ролей сотрудника**?

По текущим данным я бы начал с выбора варианта пиццы: там четыре варианта в одной карточке, цена/размер/тесто имеют прямое влияние на order payload, и результат легко проверить E2E. Но это продуктовый приоритет, а не техническое решение; нужен ваш выбор.
