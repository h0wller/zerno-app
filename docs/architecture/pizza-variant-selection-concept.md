# Концепт UX: выбор варианта пиццы

> Статус: концепт для продуктового согласования, не техническое разрешение на runtime-реализацию.
> Источник кода: `pizza` @ `4bd2fd3ad19bdcd6a060e080100e72302923814e`, 2026-11-03.
> Live DOM: `https://friday.andcoffee.online/?brand=delivery`, Firecrawl, mobile viewport 390×844, 2026-11-03. Screenshot URL был получен, но сами пиксели не удалось независимо открыть; визуальные выводы ниже основаны на исходниках и DOM, а не на просмотре screenshot.

## 1. Цель и границы задачи

Сделать выбор размера и теста пиццы однозначным до добавления в корзину: человек должен видеть, какой ровно вариант выбран, его вес и цену, а клавиатурная и скринридер-навигация не должны зависеть только от цвета или CSS-класса.

Цикл ограничен карточкой пиццы и передачей выбранного варианта в существующую корзину. PR #130 уже закрыл ценовую ясность корзины; повторно проектировать subtotal, скидки, доставку и checkout в этом цикле не требуется.

**Не-цели:**
- не менять модель данных меню, API, БД и серверный расчёт цены;
- не менять формат cart item и его идентификатор;
- не менять вертикальный rail, карточки каталога в целом, роли, checkout и промо;
- не добавлять зависимости или UI-фреймворк;
- не вводить вариант по умолчанию и не добавлять пиццу без явного выбора;
- не переписывать весь `delivery.js` или CSS.

## 2. Что делает текущая реализация

Факты, проверенные по исходникам:

1. `public/app/delivery.js: renderPizzaOptsHtml` создаёт для каждого пункта `opts[]` отдельную кнопку `.opt-btn` с `data-oi`. Внутри неё отображаются размер, тесто, вес и цена.
2. `handleDeliveryOptionClick` снимает `.sel` со всех кнопок внутри группы и переключает класс на нажатой. Поэтому повторный клик по уже выбранной кнопке снимает выбор.
3. `resolveDeliveryAddSelection` запрещает добавление пиццы без выбранной опции: показывает shake/toast и возвращает `null`.
4. `upsertDeliveryCartItem` сохраняет `oi`, `opt`, `price`, `sz`, `qty`; ключ строится как `product.id + "_" + optionIndex`. Повторное добавление того же варианта увеличивает его количество, а другой вариант создаёт отдельную позицию.
5. `syncDeliveryCartPrices` обновляет цену и подпись по актуальному меню; `server/routes/orders.js: POST /api/orders` повторно проверяет `oi` и вычисляет цену по сохранённому меню.
6. `public/app/ui/theme/160-11-canonical-grid-menu.css` уже задаёт компактную двухстрочную структуру плитки: размер/тесто и вес/цена; минимальная высота кнопки опции — 44 px.

**Проверенные тесты:**
- `tests/cart-regress.spec.js`: проверяет наличие сетки, `.sel` после клика, текущую красную заливку/белый текст и последующее добавление.
- `tests/cart-checkout-clarity.spec.js`: проверяет сохранённый вариант 35 см, подпись в корзине, обновлённую цену и увеличение количества той же позиции.
- `tests/menu-cards.spec.js`: содержит четыре комбинации размера/теста в fixture и проверяет общую геометрию карточек и минимальные touch targets.
- `playwright.config.js`: проект `chromium` запускает весь набор; `Mobile Chrome` исключает только `menu-cards.spec.js`, поэтому новый отдельный spec будет попадать в оба проекта.

**Подтверждённые пробелы в тестах:**
- нет проверки семантики radio group/checked для четырёх вариантов;
- нет проверки управления группой стрелками клавиатуры;
- нет проверки, что повторное нажатие на выбранный вариант не снимает выбор;
- нет отдельной проверки запрета добавления без выбора с неизменной корзиной;
- нет проверки двух разных вариантов одной пиццы как двух строк корзины;
- текущая матрица карточек начинается с 375 px и не проверяет короткие 320×568 и 360×640.

Текущий тест про «2 колонки» проверяет вычисленное `display: grid`, но сам по себе не доказывает фактическое число колонок. Новый тест должен измерять число колонок по geometry/computed style, если этот layout остаётся частью утверждённого концепта.

## 3. Рекомендуемый концепт

**Рекомендация**

**Сохранить компактную сетку вариантов, но превратить каждую карточку в одну нативную radio group.**

Пример смысла вариантов для одной пиццы:

| Вариант | Вес | Цена |
|---|---:|---:|
| 25 см · пышное | 415 г | 535 ₽ |
| 35 см · пышное | 750 г | 735 ₽ |
| 25 см · тонкое | 335 г | 435 ₽ |
| 35 см · тонкое | 550 г | 635 ₽ |

Это пример содержимого существующих fixture для «Маргариты», а не новый каталог или цены, задаваемые в UI. На реальной карточке значения должны по-прежнему поступать из `opts[]`.

### 3.1. Структура и поведение

- Заголовок группы: **«Размер и тесто»**.
- Внутри группы — четыре нативных radio input, по одному на каждую опцию товара. У каждой карточки собственное уникальное имя группы; выбор в одной карточке не влияет на другую.
- Радио визуально оформлено существующей плиткой, чтобы сохранить компактную сетку и визуальный язык бренда.
- Внутри плитки сохраняется порядок: размер + тесто на первой строке, вес + цена на второй.
- У radio accessible name включает полный смысл варианта: размер, тесто, вес и цену. Не полагаться на обрезанное визуальное представление текста.
- У выбранной плитки остаётся текущая заливка бренда, но выбранность также показывается отдельным видимым маркером/индикатором и нативным состоянием checked. Цвет не является единственным сигналом.
- Для клавиатуры используется нативное поведение radio group: Tab входит в группу, стрелки перемещают и выбирают соседний вариант, Space выбирает текущий. Не писать свой keydown-набор.
- Повторный клик по уже выбранному варианту не снимает выбор. Чтобы изменить выбор, пользователь выбирает другой вариант.
- **Ни один вариант не выбран по умолчанию.** Пользователь делает явный выбор до добавления.
- CTA «Добавить» остаётся отдельной кнопкой. Не переносить выбранную цену в её текст и не дублировать цену.
- При добавлении сохраняется текущий контракт `data-oi → oi → opt/price/sz`; API/БД и серверная валидация не меняются.

Radio group предпочтительнее `aria-pressed` на кнопках: это взаимоисключающий выбор из одного набора, а не набор независимых двухсостоянийных toggle-кнопок. WAI-ARIA APG описывает для radio group одновременное перемещение фокуса и выбора стрелками; `aria-pressed` относится к toggle button pattern. См. [WAI-ARIA APG: Radio Group Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) и [Button Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/).

### 3.2. Ошибка при добавлении без выбора

Текущую защиту нельзя удалять. Предлагаемое улучшение обратной связи:

1. корзина остаётся без изменений;
2. под группой появляется короткая inline-подсказка «Выберите размер и тесто»;
3. ошибка связывается с группой через `aria-describedby` и объявляется ненавязчивым live-region;
4. фокус переводится на первый radio, плитка группы получает focus-visible обводку;
5. после выбора ошибка скрывается и связь с ошибкой очищается.

Существующий toast можно оставить как дополнительную визуальную обратную связь, но не делать его единственным способом сообщить о проблеме. Это изменение остаётся гипотезой до согласования, а не фактом текущей реализации.

## 4. Почему не другие варианты

| Вариант | Плюсы | Минусы / решение |
|---|---|---|
| **A. Нативная radio group в текущей сетке** | Явная одиночная семантика, клавиатурная навигация встроена браузером, сохраняется сравнение всех цен рядом | Нужна ограниченная переработка HTML/обработчика выбора; **рекомендуется** |
| B. Оставить кнопки и добавить `aria-pressed` | Самое маленькое изменение исходной разметки | `aria-pressed` описывает toggle-состояние кнопки, а не стандартную радио-группу; клавиатурное поведение всё равно придётся проектировать и тестировать; отклоняется как основной путь |
| C. Два последовательных шага: сначала размер, затем тесто | Более крупные зоны выбора; может быть проще при большом количестве комбинаций | Скрывает одновременное сравнение цен, добавляет переход и состояние; для четырёх опций не доказано преимущество; не брать в этот цикл |

## 5. Проверяемые UX-гипотезы

- **H1 — распознавание:** пользователь по имени/внешнему виду radio может определить размер, тесто, вес и цену конкретной опции до добавления.
- **H2 — состояние:** выбранная опция остаётся выбранной, визуально и программно отличается, а выбор одной опции снимает выбранность с остальных в той же карточке.
- **H3 — ошибки:** попытка добавить без выбора приводит к понятному сообщению, фокусируемому полю и нулевым изменениям корзины.
- **H4 — мобильная плотность:** четыре плитки остаются читаемыми и достижимыми на малых экранах, без горизонтального скролла страницы и без уменьшения hit target.
- **H5 — целостность заказа:** выбранный вариант, цена, размер и количество не расходятся между карточкой, localStorage, корзиной и payload заказа.

## 6. Критерии приёмки

### UX и доступность
- Группа имеет доступное имя «Размер и тесто»; каждый radio доступен по роли и имени.
- Имя каждого radio содержит размер, тип теста, вес и цену, соответствующие одной записи `opts[]`.
- По умолчанию в каждой карточке нет выбранного radio.
- Выбрать можно только одну опцию внутри одной карточки; у соседних карточек независимые группы.
- Checked-state не зависит только от цвета; фокус виден и не обрезается.
- Tab/Shift+Tab и стрелки работают по нативному radio pattern; Space выбирает сфокусированный вариант.
- Повторный клик по текущему варианту не снимает checked.
- При отсутствии выбора add не изменяет корзину; ошибка доступна визуально и программно.
- Все опции и CTA имеют эффективную область нажатия не менее 44×44 px.

### Корзина и заказ
- Один выбранный вариант добавляется с точными `oi`, `opt`, `price`, `sz`, `qty=1`.
- Повторное добавление того же варианта увеличивает qty той же строки.
- Другой вариант той же пиццы создаёт отдельную строку.
- В корзине отображаются правильные размер/тесто и актуальная цена за штуку/строку.
- Отправляемый `oi` соответствует выбранной опции; сервер по-прежнему определяет цену из БД.
- Изменение UI не меняет promotion, subtotal, fee и checkout rules из PR #130.

### Геометрия и совместимость
- Проверить viewport: 320×568, 360×640, 375×667, 390×844, 768×1024, 1280×800.
- Нет горизонтального overflow страницы/карточки, обрезанного focus ring или наложения на CTA.
- Текст теста/размера/цены виден полностью в контрольных размерах; если отдельная подпись намеренно эллипсируется, полное значение остаётся в accessible name.
- Существующие проверки карточек, корзины, обоих брендов и мобильной геометрии остаются зелёными.

### Фикстуры и тестовые данные
- Использовать существующий pizza fixture из `tests/menu-cards.spec.js` либо локальную изолированную копию в новом spec. Не копировать hardcoded цены в production-код.

- Для проверки API payload перехватить POST /api/orders в E2E и проверить отправленный `oi`; отдельный серверный сценарий подтверждает, что server route получает индекс и вычисляет цену из БД. Новый публичный API контракт не вводится.

### Последовательность запуска после утверждения концепта
1. Написать тесты PZ-01–PZ-06 до runtime-изменения и получить ожидаемые падения на текущей разметке/поведении.
2. Реализовать минимальный HTML/state/accessibility change в `delivery.js` и соответствующий CSS, не меняя cart schema.
3. Закрыть PZ-07–PZ-12 и существующие regression suites.
4. Выполнить:
   - `npm run build:client && npx playwright test tests/pizza-variant-selection.spec.js tests/menu-cards.spec.js tests/cart-checkout-clarity.spec.js tests/cart-regress.spec.js`
   - `npm run pretest`
   - `npm run test:e2e`
   - при необходимости `npm run lint:code`
5. Проверить screenshots до/после на 320×568 и 390×844, а также production cold start в PWA/TMA. Изменение публичного JS потребует обычного bump STATIC_CACHE через `build:client`.

## 8. Риски, откат и диагностика

- **Риск ошибочного индекса:** при адаптации radio `value/data-oi` должны оставаться индексом исходной записи; тесты проверяют фактический cart item и payload, а не внутренний вызов функции.
- **Риск выбора между карточками:** каждой карточке нужен уникальный radio group name; тест выбирает вариант в двух разных карточках одновременно.
- **Риск потери focus visibility:** visually-hidden input должен оставаться доступным для клавиатуры и AT; видимый tile получает `:focus-visible` оформление.
- **Риск сдвига карточки из-за ошибки:** сообщение резервирует небольшое место или появляется без внезапного скачка; проверить row heights/CLS.
- **Риск неправильного ARIA:** не добавлять роли `radiogroup/radio` поверх нативных radio/fieldset без необходимости; не дублировать checked-state отдельными классами/атрибутами, если их можно вывести из native state.
- **Откат:** вернуть прежний renderer/handler/CSS. Cart item, API и БД не мигрируют, поэтому откат интерфейса не требует миграции данных.

## 9. Ограничения доказательств

- Код и тесты сверены по commit `4bd2fd3`; live DOM снимок подтверждает наличие четырёх option buttons и содержание элементов.
- Screenshot URL от live capture получен, но его пиксели не были визуально проверены. Нельзя пока делать подтверждённые выводы о визуальной плотности, реальном обрезании или контрасте на экране.
- Playwright, axe и ручной VoiceOver/TalkBack не запускались в рамках этого документального шага. Предложенные проверки — план, не результаты.
- Graphify подтвердил часть связей между selection/cart/order flow, но его test-link graph неполон; наличие тестов проверено непосредственно чтением Playwright-файлов.

## 10. Принятое направление и следующий шаг

Пользователь выбрал этот сценарий первым UX-циклом и подтвердил предлагаемое направление продолжением работы: **нативная radio group в текущей компактной сетке, без выбора по умолчанию, с inline-ошибкой и фокусом на первый вариант при попытке Add без выбора**.

Технический дизайн вынесен в отдельный документ: [pizza-variant-selection-design.md](./pizza-variant-selection-design.md). Он уточняет DOM-контракт, event delegation, cart/server invariants, затрагиваемые CSS owners, план миграции и тесты PZ-01–PZ-12.

Открыты только два детали до runtime PR:
- оставить legend «Размер и тесто» видимым или визуально скрыть при сохранении accessible group name; рекомендация — короткий видимый legend;
- сохранить toast вместе с inline error или оставить только inline error; решать после проверки, что screen reader не объявляет сообщение дважды.

Сам PR #131 остаётся документационным. Runtime-изменения должны идти отдельным PR после review технического draft. На текущем этапе production code и тесты не менялись.
